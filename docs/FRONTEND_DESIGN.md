# 前端页面展示与样式规范

本文档定义汽车购买推荐系统的前端体验目标、视觉系统、页面信息架构、交互状态和验收标准。前端实现必须服务于推荐主链路，重点展示“推荐为什么合理”，而不是只展示车型列表。

本文档借鉴 OpenAI 官方文章《Designing delightful frontends with GPT-5.4》的前端设计方法：先明确产品意图、用户情绪和页面叙事，再落到布局、组件、动效和状态设计。本文档不照搬任何外部页面风格，而是将方法应用到本项目的“汽车购买决策座舱”方向。

---

## 1. 设计目标与体验原则

### 1.1 前端目标

前端页面需要完成三件事：

1. 让用户顺畅提交购车需求。
2. 清楚展示推荐结果、推荐理由、不足提醒和匹配状态。
3. 在答辩时证明系统是“可解释推荐系统”，不是普通车型筛选列表。

页面设计优先级：

```text
推荐结果可解释性 > 主流程顺畅 > 信息层级清晰 > 页面美观 > 动效和装饰
```

### 1.2 体验原则

所有页面必须先回答以下问题，再设计组件：

- 用户来到这个页面要完成什么目标？
- 页面最重要的信息是什么？
- 用户为什么应该相信这些信息？
- 页面下一步主操作是什么？
- 页面在加载、无数据、错误、降级推荐时如何展示？

前端不能只堆 Element Plus 组件。Element Plus 是基础组件库，不是视觉设计本身。推荐结果、用户画像、维度评分、降级状态和历史快照必须有清晰的信息层级。

### 1.3 页面叙事

核心用户流程应形成明确叙事：

```text
我有什么购车需求
-> 系统如何理解我的需求
-> 哪些车更适合我
-> 为什么推荐这些车
-> 这些车有什么不足
-> 如果没有完全匹配，系统放宽了什么条件
-> 我可以查看详情、对比、收藏或反馈
```

## 2. 视觉方向：汽车购买决策座舱

### 2.1 设计气质

视觉方向固定为“汽车购买决策座舱”。页面应像一个理性、可信的数据决策工具，而不是汽车商城促销页，也不是纯后台管理系统。

关键词：

```text
清晰
可信
数据化
科技感
决策辅助
可解释
```

### 2.2 避免的风格

禁止把页面做成以下风格：

- 紫色渐变 + 默认卡片 + 通用 AI 页面风格。
- 商城促销风：过多价格刺激、营销 banner、抢购按钮。
- 纯后台风：只有表格和表单，没有推荐解释和视觉重点。
- 花哨动效风：动画很多但不帮助理解推荐结果。

### 2.3 情绪目标

用户看到页面后应产生的感受：

- “这个系统在认真理解我的需求。”
- “推荐结果不是随便排的，有评分和理由。”
- “即使没有完全匹配，系统也明确告诉我放宽了哪些条件。”
- “我可以继续查看详情、对比或反馈。”

## 3. Design Tokens

### 3.1 字体

采用本地优先字体栈，不引入外部 Web 字体依赖：

```css
font-family: "HarmonyOS Sans SC", "Source Han Sans SC", "Microsoft YaHei", "PingFang SC", -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif;
```

字号建议：

| 元素 | 字号 | 用途 |
| --- | --- | --- |
| Hero 主标题 | 40-48px | 首页首屏价值主张 |
| 页面标题 | 24-28px | 需求页、结果页、管理页标题 |
| 区块标题 | 18-20px | 页面内容分区 |
| 卡片标题 | 16-18px | 车型名称、统计卡片标题 |
| 正文 | 14px | 常规内容 |
| 辅助说明 | 12-13px | 弱提示、单位、说明 |
| 分数数字 | 28-40px | 综合匹配度、关键指标 |

### 3.2 色彩

核心色彩采用深蓝、青绿、琥珀三类语义色。

| Token | 用途 | 建议值 |
| --- | --- | --- |
| `--color-primary` | 主按钮、主 CTA、关键高亮 | `#2563EB` |
| `--color-primary-dark` | 深色标题、座舱背景 | `#0F172A` |
| `--color-accent` | 科技感强调、次级高亮 | `#0891B2` |
| `--color-success` | 严格匹配、成功状态 | `#16A34A` |
| `--color-warning` | 降级推荐、预算放宽 | `#F59E0B` |
| `--color-danger` | 删除、错误状态 | `#DC2626` |
| `--color-bg` | 页面背景 | `#F6F8FB` |
| `--color-card` | 卡片背景 | `#FFFFFF` |
| `--color-text` | 主文字 | `#111827` |
| `--color-muted` | 辅助文字 | `#6B7280` |
| `--color-border` | 边框 | `#E5E7EB` |

匹配状态颜色：

| 匹配状态 | 展示文案 | 颜色 |
| --- | --- | --- |
| `STRICT` | 完全匹配 | `#16A34A` |
| `RELAX_BUDGET` | 放宽预算 | `#F59E0B` |
| `RELAX_BODY_TYPE` | 放宽车型 | `#2563EB` |
| `RELAX_ENERGY_TYPE` | 放宽动力 | `#0891B2` |
| `SIMILAR_RECOMMEND` | 相似推荐 | `#64748B` |

### 3.3 间距、圆角、阴影

| Token | 建议值 | 用途 |
| --- | --- | --- |
| `--space-xs` | `4px` | 紧凑元素 |
| `--space-sm` | `8px` | 标签、轻间距 |
| `--space-md` | `16px` | 卡片内部间距 |
| `--space-lg` | `24px` | 区块间距 |
| `--space-xl` | `40px` | 页面大区块间距 |
| `--radius-sm` | `8px` | 标签、按钮 |
| `--radius-md` | `12px` | 普通卡片 |
| `--radius-lg` | `20px` | Hero、推荐重点卡片 |
| `--shadow-card` | `0 10px 30px rgba(15, 23, 42, 0.08)` | 卡片阴影 |

### 3.4 图表色板

ECharts 图表建议使用固定色板：

```text
#2563EB, #0891B2, #16A34A, #F59E0B, #64748B, #DC2626
```

图表必须有标题、单位和空状态说明。不要放无意义随机图。

## 4. 全局页面架构

### 4.1 用户端布局

用户端使用顶部导航：

```text
顶部导航：系统名称 / 首页 / 购车推荐 / 推荐历史 / 收藏 / 管理端入口
主体区域：页面内容
底部区域：项目说明，可选
```

主体最大宽度建议 `1200px`，左右留白 `24px`。

### 4.2 管理端布局

管理端使用左侧菜单 + 顶部标题：

```text
左侧菜单：车型管理 / 推荐记录 / 统计仪表盘
顶部区域：当前页面标题、管理员信息
主体区域：表格、表单、图表
```

管理端视觉保持工具型，强调稳定、清晰、可追溯。

### 4.3 演示用户模式

第一版前端不强制登录：

- 用户端默认使用演示用户身份提交需求、生成推荐、查看历史、收藏和反馈。
- 如果后端接口允许 `userId` 为空，前端可以不显式传用户 ID。
- 如果后端需要 `userId`，前端使用默认演示用户 ID：`1`。
- 管理端入口第一版可先不做复杂鉴权，后续再补 JWT 登录。

### 4.4 建议路由表

第一版路由应优先覆盖推荐闭环，完整落地页作为增强入口，不阻塞核心页面交付。

| 路由 | 页面 | 优先级 | 说明 |
| --- | --- | --- | --- |
| `/` | 首页 / 落地页 | 增强 | 可先作为简单入口页，完整落地页后置 |
| `/recommend` | 购车需求页 | 必须 | 结构化需求表单和自然语言解析入口 |
| `/recommend/result/:recordId` | 推荐结果页 | 必须 | 推荐闭环最高优先级页面 |
| `/car/:id` | 车型详情页 | 必须 | 展示车型参数、评分和推荐上下文 |
| `/history` | 推荐历史页 | 建议 | 展示历史推荐快照 |
| `/admin/cars` | 管理端车型管理 | 必须 | 车型、参数、评分维护 |
| `/admin/recommend-records` | 管理端推荐记录 | 建议 | 追溯需求、权重、分数和解释 |
| `/admin/dashboard` | 管理端统计仪表盘 | 建议 | 展示推荐效果统计 |

## 5. 完整落地页

完整落地页属于前端增强项，不阻塞第一档推荐闭环。若时间不足，`/` 可以先实现为简洁推荐入口；推荐结果页、购车需求页、车型详情页和管理端车型管理页优先级更高。

### 5.1 页面目标

用户第一次进入系统时，应在 5 秒内理解：

```text
这是一个可解释汽车推荐系统。
它不是卖车商城。
它会根据预算、场景和偏好推荐车型，并说明原因。
```

### 5.2 页面结构

落地页采用完整但克制的产品叙事：

```text
首屏 Hero
-> 推荐流程预览
-> 算法特色说明
-> 示例推荐卡片
-> 答辩/演示入口
```

### 5.3 Hero 区域

必须包含：

- 一句话价值主张。
- 简短副标题。
- 主 CTA：`开始智能推荐`。
- 次 CTA：`查看演示数据` 或 `进入管理端`。
- 汽车决策座舱视觉锚点：可用抽象仪表盘、评分卡、雷达图组合，不依赖真实汽车图片。

文案示例：

```text
用可解释评分，找到更适合你的车。
基于预算、场景和显式偏好权重，系统计算匹配度，并说明推荐理由与不足。
```

### 5.4 推荐流程预览

展示 4 步：

```text
填写需求 -> 生成画像 -> 多维匹配 -> 解释推荐
```

每一步用一句短文案说明，不要堆长段文字。

### 5.5 算法特色说明

展示 3 个特色：

- 车型参数评分：轴距、油耗、续航、安全和智能配置转成多维评分。
- 用户画像建模：多场景和显式偏好滑块转成权重。
- 降级推荐：没有完全匹配时明确说明放宽条件。

## 6. 购车需求页

### 6.1 页面目标

帮助用户提交可计算的购车需求，并理解这些选择如何影响推荐权重。

### 6.2 信息架构

```text
页面标题
-> 需求输入表单
-> 车型类型多选
-> 动力类型多选
-> 使用场景多选卡片
-> 偏好权重滑块
-> 排除品牌/车型搜索选择
-> 权重预览，可选
-> 生成推荐按钮
-> 自然语言入口，可选
```

### 6.3 表单字段

必须字段：

- 预算下限
- 预算上限
- 车型类型 `bodyTypes`，多选
- 动力类型 `energyTypes`，多选
- 座位数
- 使用场景 `scenes`，多选
- 显式偏好权重 `factorWeights`，0-10 滑块

可选字段：

- 排除品牌，搜索数据库已有品牌后点击选择
- 排除车型，搜索数据库已有车型后点击选择
- 自然语言原文

需求页不展示“推荐数量”输入，用户不填写 `topK`。推荐数量由后端使用默认值控制。

### 6.4 展示规则

- 预算前端建议用“万元”展示，提交给后端时转换为“元”。
- 车型类型使用多选按钮或复选卡片，支持 `SUV / 轿车 / MPV` 组合选择。
- 动力类型使用多选按钮或复选卡片，支持 `燃油 / 纯电 / 插混 / 增程 / 新能源` 组合选择；`新能源` 由后端展开匹配，不应写入车型表。
- 使用场景使用卡片多选，不只用下拉框。
- 偏好权重使用 0-10 滑块，维度为价格、空间、安全、能耗、智能、舒适、动力、口碑、热度。
- 全部滑块为 0 时，前端提示系统将按使用场景生成默认权重；只要有滑块大于 0，后端以归一化后的滑块值作为最终权重。
- 排除品牌和排除车型不能手动输入，应调用 `GET /api/car/brands` 和 `GET /api/car/options` 进行搜索选择。
- 用户选择场景和偏好权重后，可展示权重预览，让用户理解推荐依据。

### 6.5 场景卡片说明

| 场景 | 页面说明 |
| --- | --- |
| 城市通勤 | 更关注价格、能耗和日常便利性 |
| 家庭出行 | 更关注空间、安全和舒适性 |
| 长途自驾 | 更关注舒适、安全和续航/能耗 |
| 新手代步 | 更关注价格、安全和辅助驾驶 |
| 商务接待 | 更关注舒适、口碑和体面感 |
| 综合需求 | 各维度较均衡 |

## 7. 推荐结果页

### 7.1 页面目标

推荐结果页是前端最高优先级页面。它必须回答：

```text
推荐了什么？
为什么推荐？
哪里不足？
是否完全匹配？
如果不是完全匹配，系统放宽了什么？
```

### 7.2 信息架构

```text
用户画像摘要
-> 降级推荐提示，可选
-> 推荐结果列表
-> 维度解释和权重说明，可选
-> 重新填写需求 / 反馈 / 对比入口
```

推荐列表后续按用户可理解的语义分组：

- `完全匹配车型`：仅包含 `matchLevel = STRICT` 的结果。
- `推荐`：包含 `RELAX_BUDGET`、`RELAX_BODY_TYPE`、`RELAX_ENERGY_TYPE`、`SIMILAR_RECOMMEND` 等非严格匹配结果。

用户端应弱化降级推荐技术标签，不把 `RELAX_*` 直接作为主要标题；但单条推荐仍要根据 `matchLevel` 展示清晰匹配状态。管理端推荐记录页可以完整展示技术 `matchLevel`，用于追溯。

### 7.3 用户画像摘要

页面顶部必须展示画像文本，例如：

```text
家庭实用型用户，预算10-15万，偏好插混SUV，关注空间和安全。
```

如果有权重数据，建议展示小型权重条形图。

### 7.4 降级提示

如果出现非 `STRICT` 推荐结果，页面顶部必须展示 `fallbackMessage` 警告提示；如果接口未返回具体提示，则使用保底文案：

```text
未找到足够的完全匹配车型，系统已适度放宽部分条件，并在每个结果中标明匹配状态。
```

降级提示不能隐藏在折叠区域。

当 `recommendStatus = FALLBACK` 且结果中仍有 `STRICT` 明细时，顶部文案应表达“完全匹配车型数量不足”，不应表达“未找到完全匹配车型”。单条卡片显示“完全匹配”只允许来自 `item.matchLevel = STRICT`，不能作为 `tags` 展示。

### 7.5 推荐卡片必展示内容

每张推荐卡片必须展示：

- 排名
- 车型图片
- 品牌和车型名称
- 指导价
- 综合匹配度
- 匹配状态
- 推荐标签 `tags`
- 推荐理由 `reasonText`
- 不足提醒 `weaknessText`
- 维度评分
- 查看详情按钮
- 加入对比，可选
- 收藏，可选
- 排除该车型并重新推荐，可选

建议卡片结构：

```text
左侧：车型图片
中间：车型名称、价格、标签、理由、不足
右侧：综合匹配分、匹配状态、操作按钮
底部：维度评分条
```

匹配状态与推荐标签必须视觉分离：

- 匹配状态来自 `matchLevel`，展示为“完全匹配 / 放宽预算 / 放宽车型 / 放宽动力 / 相似推荐”。
- 推荐标签来自 `tags` 快照，只展示车型优势，例如“空间优秀”“安全配置高”“价格匹配度高”。
- `tags` 中不应出现“完全匹配”。

### 7.6 综合匹配度

综合匹配度使用醒目数字：

```text
88.6
综合匹配度
```

分数颜色：

| 分数 | 颜色 |
| --- | --- |
| >= 85 | 成功色或主色 |
| 70-84 | 主色 |
| 60-69 | 警告色 |
| < 60 | 弱化色或警告色 |

### 7.7 推荐理由与不足提醒

推荐理由和不足提醒必须直接展示：

```text
推荐理由：该车型空间表现和安全配置得分较高，符合家庭出行场景下对空间和安全的关注。
不足提醒：该车型智能配置表现一般，如果您更看重车机体验，可继续对比其他车型。
```

标签不能替代推荐理由。

### 7.8 维度评分

推荐卡片至少展示：

- 价格
- 空间
- 安全
- 能耗
- 智能
- 舒适
- 动力
- 口碑

第一版优先使用条形进度条，稳定、可读、实现成本低。

### 7.9 排除车型交互

如果支持用户排除某个推荐车型：

- 推荐卡片提供“不想看这款”操作。
- 用户确认后，将车型 ID 加入 `excludedCarIds`。
- 系统基于原需求重新生成推荐。
- 被排除车型不应在新推荐结果中再次出现。

该功能是增强体验，不阻塞第一版推荐结果页。

## 8. 推荐生成过程

### 8.1 生成中状态

推荐生成不应只是一个普通 loading。建议展示 3 步状态：

```text
1. 正在解析购车需求
2. 正在计算车型匹配度
3. 正在生成推荐理由
```

每步可使用轻量进度状态，不需要复杂动画。

### 8.2 动效规则

允许的动效：

- 页面进入轻微上浮和淡入。
- 推荐卡片列表分批出现。
- 评分条从 0 过渡到目标值。
- 降级提示出现时轻微强调。

禁止的动效：

- 大量无意义 hover。
- 长时间阻塞式动画。
- 影响答辩稳定性的复杂 3D 或粒子效果。
- 与推荐解释无关的装饰动画。

## 9. 车型详情页

### 9.1 页面目标

展示车型完整信息，并解释该车型在推荐系统中的评分来源。

### 9.2 信息架构

```text
顶部：车型图片、名称、价格、基础标签
区块 1：基础信息
区块 2：车型参数
区块 3：特征评分
区块 4：评分来源说明
区块 5：推荐上下文，可选
```

### 9.3 必展示内容

- 品牌
- 车系
- 车型名称
- 指导价
- 车型类型
- 动力类型
- 座位数
- 上市年份
- 车身尺寸
- 轴距
- 油耗/续航
- 安全配置
- 智能配置
- 多维评分

### 9.4 评分展示

详情页可使用雷达图或条形图。若时间不足，优先条形图。

必须说明评分来源，例如：

```text
空间分由轴距、车长、座位数和车型类型计算得到。
安全分由气囊、ABS、ESP 和主动安全配置计算得到。
```

## 10. 自然语言解析确认页

### 10.1 页面目标

自然语言解析是辅助填写，不直接替代用户确认。

### 10.2 信息架构

```text
原始输入
-> 系统解析结果
-> 可编辑结构化表单
-> 不支持/模糊需求提示
-> 确认并生成推荐
```

### 10.3 展示规则

- 原始输入必须展示。
- 解析出的预算、车型类型集合、动力类型集合、场景集合和 `factorWeights` 初始值必须展示。
- 用户可以修改解析结果。
- 若存在 `unsupportedTerms` 或 `ambiguousTerms`，必须提示用户确认。

## 11. 车型对比页

### 11.1 页面目标

帮助用户横向比较最多 3 款车型。

### 11.2 展示内容

- 基础参数表
- 多维评分雷达图
- 优势字段高亮
- 简短对比结论

### 11.3 对比规则

- 最多选择 3 款车型。
- 超过 3 款时提示用户移除。
- 高分维度使用主色或成功色高亮。
- 明显短板使用警告色提示。

## 12. 收藏与历史页

### 12.1 收藏页

展示用户收藏车型：

- 车型图片
- 车型名称
- 指导价
- 车型类型
- 动力类型
- 查看详情
- 取消收藏

### 12.2 历史推荐页

历史推荐不能只展示车型列表，必须展示：

- 推荐时间
- 用户画像
- 推荐状态
- 降级提示，可选
- 推荐标签快照
- 查看推荐明细入口

推荐明细展示推荐发生时保存的 `tags`、分数、理由、不足和匹配状态。不要根据当前评分规则重新生成历史标签。

## 13. 用户反馈页

### 13.1 页面目标

收集用户对推荐结果的满意度，为后台统计和后续优化提供依据。

### 13.2 表单字段

- 满意度评分，1-5
- 不满意原因
- 文字反馈
- 是否重新推荐，可选

### 13.3 不满意原因

建议选项：

- 价格偏高
- 空间太小
- 品牌不喜欢
- 动力类型不合适
- 配置不够
- 油耗或续航不满意
- 推荐结果不够准确

## 14. 管理端页面规则

### 14.1 管理端目标

管理端服务于推荐闭环，不做复杂运营后台。

管理端只保留：

```text
车型管理
推荐记录
统计仪表盘
```

### 14.2 车型管理页

必须支持：

- 新增车型
- 编辑车型
- 删除车型
- 维护参数
- 查看评分
- 重新计算评分

列表展示：

- 品牌
- 车型名称
- 指导价
- 车型类型
- 动力类型
- 座位数
- 参数完整度，可选
- 评分状态

### 14.3 推荐记录页

用于追溯推荐依据，必须展示：

- 推荐时间
- 用户需求
- 用户画像
- 权重快照
- 推荐状态
- 降级提示
- 推荐明细

推荐明细必须展示：

- 排名
- 车型
- 总分
- 各维度分
- 标签快照
- 匹配状态
- 推荐理由
- 不足提醒

### 14.4 统计仪表盘

最低完成：

- 预算区间分布
- 使用场景分布
- 热门推荐车型

增强完成：

- 显式偏好权重分布
- 满意度分布
- 不满意原因分布
- 车型类型偏好分布
- 动力类型偏好分布

图表数据结构：

- 统计图表统一消费接口返回的 `{ name, value }` 数组。
- 图表不得使用无意义随机数据；没有数据时展示空状态。
- 预算分布、场景分布、显式偏好权重分布、热门车型、满意度和不满意原因都遵循同一结构。

统计仪表盘无数据时显示空状态，不展示空白图表。

## 15. 数据状态与异常状态

### 15.1 加载状态

所有异步请求必须有加载状态：

```text
正在生成推荐...
正在加载车型详情...
正在保存反馈...
```

### 15.2 空状态

空状态必须说明原因和下一步：

```text
暂无推荐记录，您可以先填写购车需求生成推荐。
```

### 15.3 错误状态

错误状态应说明问题和操作建议：

```text
推荐生成失败，请检查需求信息后重试。
```

### 15.4 少数据状态

如果推荐结果少于预期数量，不要伪造数量。页面应提示：

```text
当前符合条件的车型较少，您可以放宽预算、车型或动力类型后重新推荐。
```

## 17. 前端验收清单

### 17.1 核心体验验收

- 用户第一次进入首页，5 秒内能理解系统是可解释汽车推荐系统。
- 用户能从首页进入购车需求页。
- 用户填写需求后能看到推荐结果。
- 推荐结果页能清楚展示为什么推荐、哪里不足、是否降级。
- 极端条件触发降级时，页面顶部有明确提示。
- 用户能进入车型详情页查看参数和评分来源。

### 17.2 数据展示验收

- 推荐结果页展示 `tags`、`matchLevel`、`reasonText`、`weaknessText`、维度分数。
- 历史页展示推荐发生时的标签、理由、不足和匹配状态快照。
- 管理端推荐记录页能复现历史推荐依据。
- 图表来自接口数据或明确测试数据。

### 17.3 实现约束验收

- 推荐算法不能写在前端。
- 前端不能只堆默认 Element Plus 组件。
- 降级推荐提示不能隐藏。
- 标签不能替代推荐理由。
- 首页不能抢占推荐结果页和需求页的实现优先级。
