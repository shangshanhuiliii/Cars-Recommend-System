# 毕业设计常问问答

本文用于毕业设计答辩准备。问题按比较严格的追问方式组织，答案以当前工程实现为准，不夸大系统能力，不把系统包装成深度学习、协同过滤或在线学习推荐。

## 一、系统定位与总体设计

### 1. 你的系统到底解决什么问题？

答：系统解决的是普通用户购车时“车型太多、参数难比较、推荐理由不透明”的问题。用户提交预算、品牌、级别、动力、座位、使用场景和九维偏好权重后，系统根据车型参数和特征评分生成推荐结果，并给出综合推荐分、推荐标签、推荐理由、不足提醒和维度评分。

### 2. 这是不是一个普通车型筛选系统？

答：不是。普通筛选只回答“哪些车型满足条件”，本系统先进行候选过滤，再用九维指标、用户权重、客观权重和 Pareto-TOPSIS 算法计算排序，并保存推荐解释和历史快照。系统重点是可解释购买推荐，而不是简单列表查询。

### 3. 你的核心业务链路是什么？

答：核心链路是“车型参数 -> 特征评分 -> 用户画像 -> 多维匹配 -> 推荐解释 -> 补充推荐 -> 推荐记录追溯”。任何功能都不能破坏这条链路，例如收藏、反馈、对比都不能反过来影响推荐排序。

### 4. 为什么选择汽车购买推荐作为毕业设计主题？

答：汽车购买决策具有多指标、多约束和强解释需求的特点。价格、空间、安全、能耗、智能、舒适、动力、口碑、热度等指标之间经常冲突，适合使用多属性决策方法，同时也能体现数据库、后端服务、前端交互、权限控制和算法解释的完整工程能力。

### 5. 系统用户分为哪些角色？

答：系统主要分为普通用户 USER 和管理员 ADMIN。普通用户可以提交需求、生成推荐、查看历史、收藏、反馈和对比车型；管理员维护车型、参数、评分、用户状态，并只读查看收藏、反馈、推荐记录、运营概览和算法可视化。

### 6. 这个系统有哪些已实现功能？

答：已实现用户注册登录、管理员登录、JWT 鉴权、结构化需求提交、推荐生成、推荐历史、车型详情、收藏、反馈、用户级车型对比、管理端车型维护、参数维护、评分重算、用户管理、推荐记录追溯、运营概览、健康检查和算法可视化。

### 7. 系统边界是什么？哪些能力你没有做？

答：系统没有实现在线学习、协同过滤、深度学习训练、真实交易闭环、经销商报价、邮箱验证码和生产级 BI。自然语言解析接口保留在后端，但当前产品前端不展示入口，也不参与主推荐流程。

### 8. 为什么不做深度学习推荐？

答：购车推荐的冷启动场景缺少足够的长期行为数据，强行使用深度学习会造成数据来源不足和解释困难。本系统采用内容特征、显式需求和多指标决策方法，更符合小规模毕业设计和可解释推荐的目标。

### 9. 为什么强调可解释性？

答：购车是高成本决策，用户不仅想知道推荐哪辆车，还需要知道为什么推荐、哪里不足、是否符合预算和场景。系统通过标签、理由、不足提醒、维度评分和历史快照，让推荐结果可以被用户理解，也可以被管理员追溯。

### 10. 系统的技术架构是什么？

答：后端采用分层结构，Controller 负责接口入口和参数校验，Service 承担业务逻辑和推荐算法，Mapper 负责数据访问，Entity、DTO、VO 分别承载数据库实体、请求对象和响应对象。前端按普通用户端和管理端分流展示，数据库保存车型、需求、推荐快照、收藏、反馈和对比数据。

## 二、推荐算法与业务规则

### 11. 当前推荐算法版本是什么？

答：当前主算法版本是 `pareto-topsis-v1`，算法名称是“主客观组合权重 + Pareto-TOPSIS”。这是系统推荐排序和解释生成的核心依据。

### 12. TOPSIS 在系统中起什么作用？

答：TOPSIS 用于计算每个候选车型相对正理想解和负理想解的接近程度。系统把接近度转换为 0-100 的 `totalScore`，作为综合推荐分，并在同一推荐组内按分数降序排序。

### 13. 什么是 `totalScore`？

答：`totalScore` 是 TOPSIS 综合推荐分，范围是 0-100。它表示车型在当前候选集、当前用户需求和当前组合权重下的综合接近程度，不是车型永久不变的绝对质量分。

### 14. `rankNo` 和 `totalScore` 谁更权威？

答：`rankNo` 更权威。后端完成分组、排序和同分处理后写入 `rankNo`，前端必须按 `rankNo` 展示推荐结果，不能再按 `totalScore`、口碑分、热度分或价格重新覆盖排序。

### 15. 为什么前端不能按分数重新排序？

答：因为后端排序不仅考虑 `totalScore`，还考虑严格匹配组优先、补充推荐组在后、同分时 Pareto 非支配辅助等规则。前端二次排序会破坏算法生成的业务语义和历史快照一致性。

### 16. Pareto 标记在系统中有什么用？

答：Pareto 标记用于识别高权重维度上的非支配车型，主要用于同分辅助排序、管理端追溯和算法可视化说明。它不作为用户端推荐标签，也不直接暴露给普通用户。

### 17. 为什么普通用户端不展示 Pareto、熵权、TOPSIS 等术语？

答：普通用户关心的是推荐是否合适、理由是什么、短板在哪里。直接展示复杂算法术语会增加理解成本。系统把算法结果转化为综合分、标签、理由和不足提醒；算法细节只在管理端和 `/algorithm-demo` 展示。

### 18. 推荐使用哪些指标？

答：推荐生成使用九维正向指标：价格、空间、安全、能耗、智能、舒适、动力、口碑和热度。其中空间到热度八维来自车型静态评分，价格分 `priceScore` 在推荐生成时根据用户预算动态计算。

### 19. 为什么 `priceScore` 不保存到 `car_feature_score`？

答：价格匹配分依赖用户预算，是动态指标。不同用户预算不同，同一车型的价格匹配程度也不同。因此 `priceScore` 只在推荐生成时计算，不写入静态车型评分表。

### 20. 八维静态评分从哪里来？

答：八维静态评分由车型基础信息和车型参数计算生成，保存到 `car_feature_score`，包括空间、安全、能耗、智能、舒适、动力、口碑和热度。管理员修改车型参数或评分规则后，需要执行评分重算。

### 21. 用户主观权重如何处理？

答：用户提交九维偏好权重后，后端会进行归一化，保证九维权重总和为 1。如果权重缺失或异常，则按默认规则兜底，避免算法计算出现异常。

### 22. 客观权重为什么要用熵权法？

答：熵权法根据当前候选集各指标差异度分配权重。某个指标差异越明显，对区分车型越有价值，客观权重就越高。它能补充用户主观偏好的不足，避免完全依赖用户随手填写的权重。

### 23. 主观权重和客观权重为什么要组合？

答：只用主观权重会过度依赖用户填写质量，只用客观权重又忽视用户真实偏好。组合权重既保留用户购车偏好，又考虑候选车型之间的客观差异，更适合可解释购车推荐。

### 24. 候选生成发生在 TOPSIS 前还是后？

答：候选生成发生在 TOPSIS 前。系统先根据预算、品牌、级别、动力、座位等条件生成候选，再对候选车型进行九维评分矩阵计算和 TOPSIS 排序。

### 25. 什么是严格匹配 `STRICT`？

答：`STRICT` 表示车型满足预算区间、车型类型、动力类型、座位等严格条件。严格匹配车型展示在“为您推荐”分组中，并且必须排在补充推荐之前。

### 26. 如果没有完全匹配车型怎么办？

答：系统会在保持核心约束的基础上生成补充推荐，例如预算放宽或相近车型推荐，并保留 `matchLevel`。补充推荐不能排在严格匹配结果之前。

### 27. 补充推荐会不会误导用户？

答：系统通过分组和匹配状态区分严格匹配与补充推荐。普通用户端用“为您推荐”和“推荐”等语义展示，管理端保留更明确的 `matchLevel` 追溯字段，避免把放宽结果伪装成完全匹配。

### 28. 每次推荐返回多少条？

答：推荐生成请求不包含推荐数量字段，后端根据候选集、分组和排序规则生成结果，每次最多保留前 30 条并写入推荐明细快照。

### 29. 候选数只有 1 个时 TOPSIS 怎么处理？

答：当候选数只有 1 个，或者正负理想解距离不可区分时，系统使用 `fallbackScore` 兜底。`fallbackScore` 根据用户主观权重和九维候选分数加权计算，只用于 TOPSIS 边界场景。

### 30. TOPSIS 分数是不是绝对分？

答：不是。TOPSIS 是相对候选集的排序方法，候选集变化会影响正理想解、负理想解和接近度。因此 `totalScore` 应理解为当前推荐任务下的综合推荐分。

### 31. 推荐标签怎么生成？

答：推荐标签来自推荐明细快照，基于表现较好的维度生成，例如空间、安全、能耗、智能等优势维度。标签不包含 Pareto、TOPSIS、熵权或 `matchLevel` 这类技术状态。

### 32. 推荐理由怎么生成？

答：推荐理由来自贡献度较高且原始维度表现不差的指标。系统选择 2-3 个用户可理解的维度生成解释，例如“空间表现较好，适合家庭出行”等，而不是把公式变量直接展示给用户。

### 33. 不足提醒怎么生成？

答：不足提醒来自用户高权重维度中与正理想解差距较大的指标。这样可以提醒用户即使某车型综合排名靠前，也可能在某些重点需求上存在短板。

### 34. 推荐记录为什么要保存快照？

答：推荐快照保证历史可追溯。后续车型参数、评分规则或数据发生变化时，历史推荐详情仍读取当时保存的分数、排序、标签、理由和不足，不重新计算覆盖历史结果。

### 35. 算法可视化接口会不会重新生成推荐？

答：不会。`/api/recommend/{recordId}/algorithm-visualization` 和管理端对应接口只读读取推荐快照和相关数据，不写数据库，不触发推荐生成，也不覆盖历史快照。

## 三、需求、接口与权限

### 36. 当前用户需求 API 使用哪些字段？

答：当前只使用 `budgetMin`、`budgetMax`、`brands`、`bodyTypes`、`energyTypes`、`seatOptions`、`scenes` 和 `factorWeights`。`minSeats`、`excludedBrands`、`excludedCarIds` 仅作为后端兼容字段保留。

### 37. 空数组在需求字段里是什么意思？

答：`brands`、`bodyTypes`、`energyTypes`、`seatOptions` 为空数组时，分别表示全部品牌、全部级别、全部动力和全部座位。`scenes` 为空时按综合需求处理。

### 38. `budgetMax = null` 表示什么？

答：表示预算上限不限。系统仍会根据预算下限和价格匹配逻辑计算动态价格分，但不会把上限作为严格约束。

### 39. 用户选择“新能源”时后端怎么处理？

答：“新能源”只作为用户需求侧的宽泛选项。后端匹配时会展开为“纯电 / 插混 / 增程”；车型表 `car_model.energy_type` 不保存“新能源”。

### 40. 为什么车型表不直接保存“新能源”？

答：因为“新能源”是用户选择的归类词，而车型真实动力类型应该更具体。数据库保存“燃油 / 纯电 / 插混 / 增程”，可以避免筛选、统计和推荐计算时语义混乱。

### 41. 用户身份从哪里来？

答：用户端接口身份必须来自 JWT 当前 USER，不能从请求参数中的 `userId` 读取。这样可以防止用户通过篡改参数访问或操作他人的需求、推荐历史、收藏、反馈和对比列表。

### 42. 管理端身份从哪里来？

答：管理端写入身份必须来自 JWT 当前 ADMIN。默认 seed 中 `admin.id = 1` 只是本地初始化主键，不能作为接口默认身份来源。

### 43. 新增 `/api/**` 接口有什么权限要求？

答：必须明确归类为公开、USER 或 ADMIN。认证拦截器采用 fail-closed 策略，未归类接口不默认放行，避免新增接口无意暴露。

### 44. 哪些接口是公开接口？

答：公开接口包括健康检查、登录注册和必要的车型资源读取，例如 `GET /api/health`、认证接口和 `GET /api/car/**`。公开不等于游客拥有完整产品能力，推荐、收藏、反馈和对比仍需 USER 身份。

### 45. 普通用户注册能创建管理员吗？

答：不能。普通用户注册只写入 `app_user`，返回 `principalType = USER`。管理员账号由 `admin` 表维护，不能通过普通注册创建或提升。

### 46. 禁用用户后会删除用户数据吗？

答：不会。管理员只维护 `app_user.status`，禁用后用户不能重新登录，但需求、推荐记录、收藏和反馈不会被删除。当前轻量 JWT 不维护服务端黑名单，已签发 token 在过期前仍可能有效。

### 47. 推荐生成请求为什么不包含推荐数量字段？

答：推荐数量由后端根据候选集、分组和排序规则控制，最多保存 30 条。这样可以避免前端或用户任意改变推荐规模，破坏推荐结果的一致性。

### 48. 需求提交后是否立即生成推荐？

答：主流程是用户先提交结构化需求，后端保存需求并生成画像和权重，然后调用推荐生成接口生成推荐记录。自然语言解析接口不保存需求，也不直接生成推荐。

### 49. 推荐历史能不能查看别人的记录？

答：普通用户不能。用户端推荐历史只返回当前 JWT 用户自己的推荐记录。管理员可以通过管理端推荐记录接口查看全量记录或按用户筛选。

### 50. 反馈接口如何保证安全？

答：反馈接口需要 USER 权限，并且只能对当前用户自己的推荐记录提交或查看反馈。同一用户同一推荐记录只保留一条反馈，重复提交会覆盖原反馈。

## 四、数据库与数据一致性

### 51. 数据库核心表有哪些？

答：核心表包括 `app_user`、`admin`、`car_model`、`car_param`、`car_feature_score`、`user_demand`、`recommend_record`、`recommend_item`、`user_compare_car`、`user_favorite` 和 `recommend_feedback`。

### 52. `recommend_record` 和 `recommend_item` 分别保存什么？

答：`recommend_record` 保存一次推荐任务的总体快照，例如用户、需求、状态和时间；`recommend_item` 保存推荐明细，包括车型、排名、综合分、价格分、匹配状态、标签、理由、不足和维度分等。

### 53. 为什么不能只保存推荐车型 ID？

答：只保存车型 ID 无法追溯当时为什么推荐、排序是多少、分数是多少、短板是什么。车型数据和评分规则后续可能变化，所以必须保存推荐依据快照。

### 54. `car_model` 和 `car_param` 怎么分工？

答：`car_model` 保存车型基础展示和过滤字段，例如品牌、车系、车型名、价格、级别、动力、图片等；`car_param` 保存更细的参数配置，用于详情展示和特征评分来源追溯。

### 55. `car_feature_score` 为什么单独成表？

答：车型评分是由基础信息和参数计算得到的派生结果，单独保存可以避免每次推荐都重复计算静态评分，也方便管理员重算和查看评分结果。

### 56. 修改车型参数后会自动影响推荐历史吗？

答：不会覆盖历史推荐。修改车型参数后，如果管理员执行评分重算，会影响之后的新推荐；历史详情仍读取当时保存的推荐快照。

### 57. 导入车型数据会不会删除旧数据？

答：不会。管理端 JSON 数据导入按 `brand + series + modelName + launchYear` 匹配未删除车型，存在则更新，不存在则新增，不会删除旧车型，也不会修改收藏、对比、反馈、推荐历史或推荐明细快照。

### 58. 导入车型后为什么还要评分重算？

答：导入只维护 `car_model` 和 `car_param`。新增或更新车型要参与推荐评分链路，必须执行全部车型评分重算，生成或更新 `car_feature_score`。

### 59. 收藏数据如何保存？

答：收藏保存在 `user_favorite` 表，使用 `user_id` 和 `car_id` 关联，取消收藏采用软删除。重复收藏幂等返回成功，收藏不参与推荐排序。

### 60. 对比数据为什么不放 localStorage？

答：当前设计要求对比列表属于当前登录 USER 的后端持久化数据，保存在 `user_compare_car`。这样用户换设备登录后仍能读取自己的对比列表，也能通过后端身份校验避免操作他人数据。

### 61. 对比最多几辆车？

答：每个用户当前最多保存 3 辆未删除对比车型。对比只读取车型基础信息、参数和静态评分，不触发推荐生成，不影响推荐排序。

### 62. 反馈数据如何保存？

答：反馈保存在 `recommend_feedback`，包括满意度、原因标签和文字评论。文字评论最长 500 字，重复提交按覆盖处理。

### 63. 反馈会不会改变算法？

答：不会。反馈只进入统计和管理端查看，不自动修改用户权重、车型评分、推荐记录、推荐明细或排序。系统没有做在线学习。

### 64. 为什么使用软删除？

答：软删除可以保留历史关系和追溯能力，避免删除车型、收藏或对比记录时破坏已有推荐历史和统计关联。系统统一使用 `deleted` 字段标记软删除。

### 65. 本地 seed 账号有什么注意点？

答：本地默认普通用户是 `user / user123456`，管理员是 `admin / admin123456`。它们的 ID 只作为本地种子主键，不作为接口默认身份来源。

## 五、前端交互与用户体验

### 66. 前端最重要的页面是什么？

答：推荐结果页最重要。它必须展示推荐车型、综合推荐分、推荐标签、推荐理由、不足提醒、维度评分、查看详情、收藏、加入对比和反馈入口。

### 67. 推荐结果页如何排序？

答：默认必须按后端 `rankNo` 升序展示。即使页面提供“价格从低到高演示”，也只能作用于当前推荐记录中的辅助查看视图，关闭后必须恢复 `rankNo` 排序。

### 68. 为什么普通操作不用顶部 toast？

答：项目规范要求收藏、取消收藏、加入对比、提交反馈等普通操作通过按钮状态、卡片内提示、表单区域提示或页面内状态条表达。这样反馈更贴近操作位置，避免顶部 toast 与推荐主信息割裂。

### 69. 未登录用户访问推荐页怎么办？

答：前端保留当前目标页面作为背景，通过 `auth` 查询参数打开登录或注册浮窗，并保留合法 `redirect`。登录成功后进入原目标地址，不强制把背景切换到首页。

### 70. 为什么不用独立登录页？

答：产品前端使用全局登录 / 注册浮窗承载普通用户登录、注册和管理员登录模式。`/login`、`/register`、`/admin/login` 只作为兼容入口，核心体验是不中断用户当前访问目标。

### 71. 管理员登录后进入哪里？

答：管理员登录后默认进入 `/admin/cars`。管理员不显示普通首页入口，不能进入普通首页，右上角或侧栏身份固定显示“管理员”。

### 72. 普通用户端为什么不展示算法可视化入口？

答：普通用户端的目标是购车决策，不是算法教学。算法可视化属于管理端只读工具，展示权重、矩阵、Pareto 和 TOPSIS 过程，用于追溯和答辩说明。

### 73. 首页承担什么职责？

答：首页面向普通用户，突出核心购车推荐入口和产品能力介绍，不承担健康检查、后台排查或复杂算法说明职责。推荐历史、收藏和对比由导航栏进入。

### 74. 车型详情页展示什么？

答：车型详情页展示横屏大图、基础信息、参数和特征评分。从推荐结果进入时应保留“返回推荐结果”路径，方便用户回到对应推荐记录。

### 75. 收藏页和对比页会影响推荐吗？

答：不会。收藏只记录用户关注车型，对比只帮助用户横向比较 1-3 款车型，它们都不写入推荐权重，也不改变 `pareto-topsis-v1` 排序。

### 76. 推荐历史页为什么不能重新生成标签？

答：历史页必须展示推荐发生时保存的快照信息。如果重新生成标签或分数，就会造成历史结果和用户当时看到的结果不一致，破坏追溯可信度。

### 77. 用户端为什么要展示不足提醒？

答：只展示优点容易让推荐结果显得片面。购车决策需要知道短板，系统根据用户高权重维度中的差距生成不足提醒，帮助用户理性比较。

### 78. 管理端的定位是什么？

答：管理端服务于推荐数据基础、推荐追溯和统计，不做复杂运营后台。它维护车型、参数和评分，查看用户状态、推荐记录、收藏统计、反馈记录和系统健康状态。

### 79. 管理员能不能代用户收藏或反馈？

答：不能。管理端收藏车型和反馈记录页面是只读追溯页面，不提供取消收藏、删除反馈或代用户操作能力。

### 80. 前端菜单隐藏是不是安全边界？

答：不是。菜单隐藏只是用户体验层面的控制，真正安全边界在后端 JWT 鉴权、角色权限和接口归类上。

## 六、安全、测试与工程质量

### 81. 系统如何防止越权访问？

答：后端通过 JWT 识别当前主体和角色，USER 接口只能访问当前用户数据，ADMIN 接口需要管理员 token。新增 `/api/**` 接口必须显式归类，未归类接口默认拒绝。

### 82. 为什么不能通过 `userId` 参数操作数据？

答：如果接口相信 `userId` 参数，用户可以篡改参数访问他人数据。系统规定用户端身份必须来自 JWT 当前 USER，请求体或查询参数中的 `userId` 不能覆盖当前身份。

### 83. 系统如何处理管理员和普通用户的隔离？

答：普通用户和管理员分别存储在 `app_user` 和 `admin` 表中，登录后返回不同 `principalType`。前端路由按身份分流，后端接口按角色校验权限。

### 84. 密码和密钥方面有什么要求？

答：项目不提交 `application-local.yml`、`.env`、`.env.local`，不提交真实密码、token、密钥或生产连接信息。种子账号只用于本地开发和演示。

### 85. 真实数据库可以直接操作吗？

答：不能随意操作。除非明确确认目标库和影响范围，否则不对真实 MySQL 执行迁移、重建、清空或删除数据。本地开发库重建前也要说明会删除需求、推荐记录、对比、收藏和反馈等数据。

### 86. 修改推荐算法时需要测什么？

答：至少要覆盖预算边界、动力“新能源”展开、场景权重兜底、权重归一化、价格分动态计算、Pareto 非支配识别、TOPSIS 排序稳定性、STRICT 组优先、最多 30 条、`rankNo` 连续和用户端标签不含算法术语。

### 87. 修改 API 时需要同步做什么？

答：需要同步更新接口文档、前后端调用、权限归类和测试。不能只改代码不改文档，因为本项目文档是工程协作和答辩说明的重要依据。

### 88. 修改数据库字段时需要同步做什么？

答：需要同步更新数据库脚本、实体、Mapper、Service、接口响应、前端展示、数据库文档和相关测试。涉及推荐链路字段时还要确认历史快照不被破坏。

### 89. 为什么推荐算法必须在 Service 层？

答：Controller 只负责接收请求和参数校验，前端只负责展示。推荐算法属于核心业务逻辑，必须在 Service 层实现，便于复用、测试、维护和保证权限边界。

### 90. 为什么不能在前端重新计算推荐？

答：前端重新计算会绕过后端统一算法、权限、快照和排序规则，也会导致历史追溯不一致。前端只能展示后端生成并保存的推荐结果。

### 91. 系统如何保证推荐结果可追溯？

答：推荐生成时保存 `recommend_record` 和 `recommend_item` 快照，包括需求、权重、分数、排序、匹配状态、标签、理由和不足。历史详情、管理端推荐记录和算法可视化都读取这些快照。

### 92. 如果评分规则变了，历史推荐怎么办？

答：历史推荐不重新计算。评分规则变化只影响后续新推荐，历史仍展示当时保存的快照。这是为了保证用户历史记录和管理端审计一致。

### 93. 系统有没有性能风险？

答：主要风险在推荐生成时需要加载候选车型并计算九维矩阵、权重和排序。当前毕业设计规模下可以接受；后续如果车型量增大，可以从候选过滤、索引、缓存静态评分和分页追溯等方向优化。

### 94. 数据量不大时做推荐有没有意义？

答：有意义，但定位要准确。本系统不是大规模商业推荐平台，而是面向冷启动购车场景的可解释决策辅助系统。重点在多指标建模、权重计算、推荐解释和工程闭环。

### 95. 你的系统最容易被质疑的点是什么？

答：最容易被质疑的是推荐评分规则和权重是否足够客观。我的回答是：系统没有声称分数代表真实市场绝对价值，而是基于明确指标、显式权重和候选集差异进行可解释排序，并通过快照保留计算依据。

### 96. 如果老师说推荐理由是模板化的，你怎么回答？

答：推荐理由确实是规则生成，不是大模型自由生成。这样做的优点是可控、可追溯、不会编造信息，并且能和维度贡献、权重、评分直接对应，适合毕业设计中的确定性推荐解释。

### 97. 如果老师说收藏和反馈为什么不影响推荐，你怎么回答？

答：因为当前系统定位是基于显式需求和车型内容特征的冷启动推荐。收藏和反馈数据量不足时直接影响排序容易引入噪声，所以本阶段只进入统计和追溯，不做在线学习，这是有意控制系统边界。

### 98. 如果老师问系统创新点是什么？

答：创新点不是发明新算法，而是把结构化购车需求、九维特征评分、主客观组合权重、Pareto-TOPSIS 排序、推荐解释和历史快照追溯整合成完整工程链路。系统同时兼顾用户可理解性和管理端可追溯性。

### 99. 如果老师问不足和改进方向是什么？

答：不足包括车型数据规模有限、评分规则仍依赖人工设定、反馈未进入学习闭环、没有接入真实成交和价格波动数据。后续可以扩展数据源、引入更严格的评分校准、做离线评估、在数据量足够后尝试行为反馈建模。

### 100. 如果只用一句话总结你的系统，你会怎么说？

答：这是一个面向冷启动购车场景的可解释汽车推荐系统，它用结构化用户需求、车型特征评分和 Pareto-TOPSIS 多指标决策方法生成可追溯的购车推荐，而不是简单车型筛选或不可解释的黑盒排序。
