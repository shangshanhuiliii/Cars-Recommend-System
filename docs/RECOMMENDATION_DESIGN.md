# 推荐闭环设计

本文档描述推荐系统的闭环设计、模块职责和边界。当前主算法的详细公式、流程和伪代码统一维护在 `RECOMMENDATION_ALGORITHM_UPGRADE.md`；车型特征评分规则维护在 `RECOMMENDATION_ALGORITHM.md`。数据库字段见 `DATABASE_DESIGN.md`，接口约定见 `API_DESIGN.md`，实施阶段见 `IMPLEMENTATION_TASKS.md`。

## 1. 推荐目标

系统推荐能力围绕以下闭环实现：

```text
车型特征评分 -> 用户画像建模 -> 多维匹配计算 -> 推荐解释生成 -> 无匹配降级处理 -> 推荐记录追溯
```

推荐结果必须满足：

- 来自真实车型数据和评分规则。
- 能说明推荐理由和不足提醒。
- 能标识严格匹配或补充推荐的匹配状态。
- 能保存推荐依据，支持历史回查。

## 2. 算法类型

本项目采用：

```text
基于主客观组合权重与 Pareto-TOPSIS 的可解释汽车推荐算法
```

该算法版本为 `pareto-topsis-v1`。它适合当前项目，因为车型参数和用户需求都可以结构化，候选车型数量适合多指标决策方法，且推荐结果需要在论文和答辩中解释清楚。

当前推荐排序采用主客观组合权重、Pareto 非支配识别和 TOPSIS 多指标决策排序。详细公式只在 `RECOMMENDATION_ALGORITHM_UPGRADE.md` 中维护。

本项目不采用：

- 协同过滤。
- 深度学习推荐。
- 在线学习推荐。

原因是当前系统缺少真实用户长期点击、收藏、购买和反馈行为数据，复杂模型会增加数据依赖和解释成本，不符合当前 MVP 目标。

## 3. 设计主线

推荐主线分为六步：

1. 车型侧：从 `car_model` 和 `car_param` 计算 `car_feature_score`。
2. 用户侧：从 `user_demand` 生成画像文本和九维权重。
3. 严格过滤：按预算上限、车型集合、动力集合、最低座位数、排除品牌和排除车型筛选候选。
4. 匹配评分：动态计算 `priceScore`，生成主客观组合权重，使用 Pareto-TOPSIS 计算 `totalScore`。
5. 解释生成：生成 `tags`、`reasonText` 和 `weaknessText`。
6. 追溯保存：保存 `recommend_record` 和 `recommend_item` 快照。

详细公式和伪代码见 `RECOMMENDATION_ALGORITHM_UPGRADE.md`。

## 4. 车型特征评分职责

车型特征评分负责把车型参数转成 0-100 分的特征向量：

- 空间
- 安全
- 能耗
- 智能
- 舒适
- 动力
- 口碑
- 热度

`priceScore` 不属于车型静态评分，不写入 `car_feature_score`。价格匹配分依赖用户预算，只能在推荐生成阶段动态计算。

`comfortScore` 当前采用组合估算，公式维护在 `RECOMMENDATION_ALGORITHM.md`。如果后续增加座椅、悬架、隔音、空调等字段，可扩展舒适性评分来源。

## 5. 用户画像职责

用户需求当前使用多选和显式权重模型：

- `bodyTypes`
- `energyTypes`
- `scenes`
- `factorWeights`
- `minSeats`
- `budgetMin`
- `budgetMax`
- `excludedBrands`
- `excludedCarIds`

画像服务负责：

- 校验需求字段。
- 处理多场景默认权重。
- 归一化九维显式偏好权重。
- 生成 `profileText`。
- 保存权重快照。

## 6. 推荐匹配职责

推荐服务负责：

- 加载审核通过、未删除且有评分的车型。
- 执行严格过滤。
- 执行分级补充推荐。
- 动态计算价格分。
- 计算 TOPSIS 推荐分。
- 生成标签、理由和不足。
- 分组排序。
- 保存推荐记录和推荐明细。

推荐生成接口不接收推荐数量字段。系统返回全部符合当前分组规则的候选：

- `STRICT` 组：全部完全匹配车型。
- 推荐组：全部非 `STRICT` 补充推荐车型。

最终展示顺序为 `STRICT` 组在前，推荐组在后；后端每组内部先按 `totalScore desc` 排序，再用 Pareto 非支配标记、口碑分、热度分做同分辅助排序并写入 `rankNo`。前端每组内部必须按后端返回的 `rankNo` 升序展示，不按 `totalScore`、口碑分或热度分二次排序。`totalScore` 字段语义为 TOPSIS 综合推荐分。

## 7. 降级推荐职责

降级推荐是候选补充，不是覆盖严格匹配结果。

匹配阶段包括：

- `STRICT`
- `RELAX_BUDGET`
- `RELAX_BODY_TYPE`
- `RELAX_ENERGY_TYPE`
- `SIMILAR_RECOMMEND`

基本原则：

- 同一车型只进入推荐集一次。
- `matchLevel` 保留首次进入推荐集的阶段。
- 排除品牌、排除车型和最低座位数不参与放宽。
- 用户端弱化技术性降级提示。
- 管理端和历史详情保留 `matchLevel`、`recommendStatus` 和 `fallbackMessage` 用于追溯。

各阶段边界和映射规则见 `RECOMMENDATION_ALGORITHM_UPGRADE.md`。

## 8. 推荐解释职责

推荐解释由三类内容组成：

- `tags`：推荐亮点摘要，只展示优势标签。
- `reasonText`：结合 `finalWeight` 和 TOPSIS 归一化表现，从贡献度较高的维度说明为什么推荐。
- `weaknessText`：结合用户高权重维度和正理想解差距，说明潜在不足；无明显短板时使用均衡保底文案。

`tags` 不允许包含匹配状态或降级状态，例如“完全匹配”“降级推荐”“放宽预算”“放宽车型”“放宽动力”“相似推荐”。`matchLevel` 不能混入 `tags`。

## 9. 推荐追溯职责

一次推荐必须保存：

- 用户需求 ID。
- 画像文本。
- 权重快照。
- 推荐状态。
- 降级提示追溯字段。
- 推荐明细的排名、车型、总分、价格分、各维度分、标签、理由、不足和匹配状态。

历史详情必须读取保存快照，不得重新计算历史推荐结果、分数、标签、理由、不足或 `matchLevel`。

## 10. 前端展示边界

用户端推荐结果页按用户可理解的语义展示：

- 完全匹配车型。
- 推荐。

用户端默认不展示 `fallbackMessage` 顶部强提示，不展示“降级推荐”等技术标签。管理端推荐记录页可以完整展示 `recommendStatus`、`fallbackMessage` 和 `matchLevel`。

用户端每组内部以后端 `rankNo` 为唯一排序权威。前端只负责分组和展示，不重新计算、不重新排序推荐结果。用户端需说明：不同分组之间优先看条件匹配状态，同组内部按综合推荐分排序；Pareto 仍保留为同分辅助排序和答辩/管理追溯信息。

## 11. 增强功能边界

自然语言解析、车型对比、收藏、用户反馈和管理端统计已经作为增强能力接入，但它们不改变当前推荐排序规则：

- 自然语言解析只生成结构化表单草稿，用户确认后才保存需求并生成推荐。
- 车型对比只读，不调用推荐生成，不触发评分重算。
- 收藏只维护收藏关系，不影响推荐排序。
- 用户反馈只进入统计，不自动修改权重、车型评分或推荐排序。
- 管理端统计来自真实数据，不使用随机数或前端假数据。

图片上传、Redis、复杂权限、深度学习推荐和在线学习推荐仍只作为后续展望。
