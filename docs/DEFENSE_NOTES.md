# 答辩材料整理

本文档用于论文写作和答辩准备。当前主算法详细公式不在本文档重复维护，统一见 `RECOMMENDATION_ALGORITHM_UPGRADE.md`。

## 1. 项目一句话定位

本项目是一个面向冷启动购车场景的可解释汽车推荐系统，基于车型内容特征、用户结构化需求和主客观组合权重，使用 Pareto-TOPSIS 多指标决策方法给出推荐结果、理由、不足和历史追溯。

## 2. 与普通汽车筛选的区别

普通筛选通常只按预算、车型、动力等条件过滤，返回“满足条件的车型列表”。本系统在硬性过滤之后继续计算九维指标评分、用户偏好权重、候选集客观差异、Pareto 非支配关系和 TOPSIS 综合匹配度，并保存推荐理由、不足提醒和匹配状态。

因此，系统不仅回答“哪些车符合条件”，还回答“哪些车更适合当前用户、为什么推荐、哪里存在短板、如果没有完全匹配怎么办、历史结果能否复现”。

## 3. 推荐算法亮点

- 当前主算法：基于主客观组合权重与 Pareto-TOPSIS 的可解释汽车推荐算法。
- 算法版本：`pareto-topsis-v1`。
- 冷启动友好：不依赖大量用户点击、收藏或购买行为。
- 内容特征驱动：车型参数被转成价格、空间、安全、能耗、智能、舒适、动力、口碑、热度九维指标。
- 权重可解释：用户显式偏好或场景模板生成 `subjectiveWeight`，熵权法生成 `objectiveWeight`，再通过 `alpha` 得到 `finalWeight`。
- 排序更稳健：Pareto 非支配优先避免单一高分掩盖重点维度短板，TOPSIS 计算相对正负理想解的接近度。
- 结果可追溯：推荐记录保存算法版本、权重快照、分数快照、理由、不足、标签和匹配状态。
- 阶段 9.8 新增 `/algorithm-demo` 答辩页，通过只读接口展示权重、候选阶段、九维矩阵、Pareto、TOPSIS、解释和快照追溯，不改变推荐主链路。

## 4. 为什么不用深度学习或协同过滤

本项目面向本科毕设和冷启动购车推荐。系统没有足够真实用户行为数据支撑深度学习或协同过滤训练，强行使用复杂模型会增加数据依赖、解释难度和工程风险。购车推荐本身是多约束、多指标、多目标权衡问题，使用可解释的内容特征推荐和多指标决策方法更适合当前数据条件，也更便于答辩解释。

## 5. 当前推荐流程讲解

1. 用户提交结构化需求：预算、车型类型集合、动力类型集合、场景、最低座位数、偏好权重、排除品牌和排除车型。
2. 后端生成画像文本和用户画像主观权重。
3. 系统加载审核通过、未删除且有特征评分的车型。
4. 执行硬性过滤和分阶段候选补充：`STRICT`、`RELAX_BUDGET`、`RELAX_BODY_TYPE`、`RELAX_ENERGY_TYPE`、`SIMILAR_RECOMMEND`。
5. 动态计算 `priceScore`，并与八个静态特征评分组成九维决策矩阵。
6. 计算 `subjectiveWeight`、`objectiveWeight`、`finalWeight` 和 `alpha`。
7. 使用 Pareto 非支配标记调整组内优先级。
8. 使用 TOPSIS 计算 `totalScore`，即综合匹配度。
9. 后端按 `STRICT` 组在前、推荐组在后生成 `rankNo`。
10. 生成 `tags`、`reasonText`、`weaknessText` 并保存推荐快照。
11. 前端只按“完全匹配车型 / 推荐”分组和后端 `rankNo` 展示，不重新排序。
12. 答辩时可进入 `/algorithm-demo` 选择推荐记录，展示推荐快照对应的算法过程和临时重构的 Pareto-TOPSIS 中间值。

## 6. 三个答辩演示案例

### 6.1 家庭出行

输入建议：

- 预算：10-15 万。
- 车型：SUV / MPV。
- 动力：插混 / 增程 / 新能源。
- 场景：家庭出行、长途自驾。
- 偏好：空间、安全、舒适较高。

讲解重点：

- 展示系统如何把家庭场景转成更高的空间、安全和舒适权重。
- 展示 `新能源` 只作为用户侧宽泛偏好，实际匹配纯电、插混、增程。
- 展示完全匹配车型和推荐补充车型分组。
- 讲解推荐理由来自高贡献维度，不足提醒来自理想解差距。

### 6.2 城市通勤

输入建议：

- 预算：8-12 万。
- 车型：轿车 / SUV。
- 动力：燃油 / 纯电。
- 场景：城市通勤、新手代步。
- 偏好：价格、能耗、智能较高。

讲解重点：

- 展示动态 `priceScore` 和能耗维度对排序的影响。
- 展示 TOPSIS 综合匹配度不是单看价格或销量。
- 展示前端使用“综合匹配度”，不暴露 TOPSIS、Pareto、熵权等技术术语。

### 6.3 极端条件

输入建议：

- 预算较低。
- 车型：SUV。
- 动力：纯电。
- 最低座位数：7 座。
- 偏好：空间、安全较高。

讲解重点：

- 预期可能没有 `STRICT` 结果或严格结果很少。
- `minSeats`、排除品牌和排除车型不会被降级放宽。
- 系统通过推荐组补充相近车型，管理端和历史详情可以追溯 `matchLevel` 与 `fallbackMessage`。
- 用户端不显示强技术提示，只用“完全匹配车型 / 推荐”表达结果。

## 7. 答辩常见问题回答

### 这和普通筛选有什么区别？

普通筛选只过滤条件，本系统还计算九维评分、主客观组合权重、Pareto 非支配关系和 TOPSIS 综合匹配度，并生成理由、不足和可追溯推荐记录。

### 你的推荐算法是什么？

当前主算法是“基于主客观组合权重与 Pareto-TOPSIS 的可解释汽车推荐算法”，版本为 `pareto-topsis-v1`。它不是深度学习、协同过滤或在线学习。

### 权重怎么来的？

用户显式滑块或场景模板生成 `subjectiveWeight`；候选车型在九维指标上的差异通过熵权法生成 `objectiveWeight`；两者按 `alpha` 组合为 `finalWeight`。

### 为什么要用熵权法？

用户偏好是主观的，但候选车型在不同指标上的区分度不同。熵权法可以让差异更大的指标获得更高客观权重，减少只依赖用户主观权重带来的偏差。

### 为什么要用 TOPSIS？

购车是多指标权衡，不适合只按单一字段排序。TOPSIS 通过计算候选车型接近正理想解、远离负理想解的程度，得到更符合多指标决策逻辑的综合匹配度。

### 为什么不用深度学习？

系统缺少长期真实用户行为数据，深度学习模型难以训练和解释。当前任务更适合冷启动内容推荐和可解释多指标决策方法。

### 推荐理由怎么生成？

推荐理由来自贡献度较高的维度，例如最终权重高且车型标准化表现好的维度；不足提醒来自用户关注维度中与正理想解差距较大的维度。

### 算法可视化页会不会重新生成推荐？

不会。阶段 9.8 的算法可视化页只调用 `GET /api/recommend/{recordId}/algorithm-visualization`，读取已保存的 `recommend_record`、`recommend_item` 和关联需求、车型数据。页面展示的排序、`totalScore`、`tags`、`reasonText` 和 `weaknessText` 以历史快照为准，Pareto 标记和 TOPSIS 距离只基于快照矩阵临时重构用于答辩展示，不写入数据库。

### 历史推荐为什么可以追溯？

每次推荐都会保存 `recommend_record` 和 `recommend_item` 快照，包括算法版本、权重快照、总分、维度分、标签、理由、不足和 `matchLevel`。历史详情读取快照，不重新计算。

### 如果没有完全匹配车型怎么办？

系统会保留硬性约束中的最低座位数、排除品牌和排除车型，然后按预算、车型类型、动力类型和相似推荐阶段补充候选。用户端显示“推荐”组，管理端可以查看具体 `matchLevel` 和 `fallbackMessage`。

### 算法有什么不足和展望？

TOPSIS 分数依赖当前候选集，候选集变化会影响综合匹配度；熵权法在候选很少时不稳定，因此需要兜底；当前 Pareto 只做排序标记，不持久化中间结果。后续可以扩展自然语言解析、用户反馈闭环、车型对比和更细粒度参数数据，但不把当前系统包装成深度学习或在线学习。

## 8. 当前不足与展望

- 自然语言解析尚未完成，当前以结构化购车需求为主。
- 收藏、用户反馈和车型对比属于后续增强功能。
- 演示车型数据用于系统验证，不代表真实市场结论。
- `paretoDominated`、TOPSIS 距离等中间结果第一版不单独入库，管理端主要通过权重快照、维度分、`totalScore` 和 `rankNo` 追溯。
- 阶段 9.8 答辩页会基于历史快照临时重构 `paretoDominated`、TOPSIS 距离、贡献度和差距，用于展示算法过程；这些中间值仍不持久化。
