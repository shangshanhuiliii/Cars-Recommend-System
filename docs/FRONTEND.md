# 前端文档

本文档描述当前前端页面结构、交互规则和展示规范。前端实现必须服务于推荐主链路，重点展示“为什么推荐”和“哪里不足”，不能退化成普通车型列表。

## 体验目标

前端需要完成：

1. 让用户顺畅提交购车需求。
2. 清楚展示推荐结果、综合推荐分、推荐理由、不足提醒和维度评分。
3. 让推荐历史、管理端和算法可视化页面能够回查推荐依据。

推荐结果页是用户端最重要页面。它必须展示：

- 综合推荐分。
- 推荐标签。
- 推荐理由。
- 不足提醒。
- 维度评分。
- 查看详情入口。

## 视觉方向

视觉方向为“汽车购买决策座舱”。页面应像理性、可信的数据决策工具，而不是汽车商城促销页或纯后台表格。

关键词：

```text
清晰
可信
数据化
科技感
决策辅助
可解释
```

避免：

- 紫色渐变和通用 AI 页面风格。
- 过多促销、价格刺激和营销按钮。
- 只有表格和表单、没有推荐解释的信息堆叠。
- 与理解推荐结果无关的复杂动效。

## 全局布局

用户端顶部导航：

```text
系统名称 / 首页 / 购车推荐 / 车型对比 / 我的收藏 / 推荐历史 / 管理端入口
```

主体区域建议最大宽度 `1200px`，左右留白 `24px`。

管理端布局：

```text
左侧菜单：车型管理 / 推荐记录 / 统计仪表盘 / 系统健康检查 / 算法可视化
顶部区域：当前页面标题、管理员信息
主体区域：表格、表单、图表
```

普通操作成功或失败不使用顶部 toast。收藏、取消收藏、加入对比、提交反馈、自然语言解析等操作使用按钮状态、卡片内提示、表单区域提示或页面内状态条表达结果。

## 首页

首页是面向普通用户的产品首页，不承担运行检查、管理端排查或算法说明职责。

首页结构：

- 顶部大轮播图，至少包含 3 张内容，引导开始推荐、查看历史和车型对比。
- 轮播图需要有明确主视觉、标题层级、CTA 和辅助信息，不应只是普通卡片堆叠。
- 推荐入口区，提供开始购车推荐、查看推荐历史、我的收藏和车型对比入口。
- 核心能力区，简洁展示多维车型评分、个性化偏好权重、推荐理由、不足提醒、收藏与对比。

首页不得调用 `GET /api/health`，不得展示健康检查状态；不得把算法可视化作为首页主入口；不得展示复杂算法术语。

## 购车需求页

页面目标：帮助用户提交可计算的购车需求，并理解这些选择如何影响推荐权重。

必须字段：

- 预算下限。
- 预算上限。
- 车型类型 `bodyTypes`，多选。
- 动力类型 `energyTypes`，多选。
- 最低座位数 `minSeats`。
- 使用场景 `scenes`，多选。
- 显式偏好权重 `factorWeights`，0-10 滑块。

可选字段：

- 排除品牌，搜索数据库已有品牌后点击选择。
- 排除车型，搜索数据库已有车型后点击选择。
- 自然语言原文。

展示规则：

- 预算前端用“万元”展示，提交给后端时转换为元。
- 车型类型支持 `SUV / 轿车 / MPV` 组合选择。
- 动力类型支持 `燃油 / 纯电 / 插混 / 增程 / 新能源` 组合选择。
- `新能源` 由后端展开匹配，不写入车型表。
- 使用场景使用卡片多选，不只用下拉框。
- 偏好权重维度为价格、空间、安全、能耗、智能、舒适、动力、口碑、热度。
- 全部滑块为 0 时，提示系统将按使用场景生成默认权重。
- 只要有滑块大于 0，后端以归一化后的滑块值作为主观权重。
- 不展示推荐数量输入。

自然语言解析入口：

- 用户输入一句话需求后调用 `POST /api/user/demand/parse-text`。
- 返回结果回填结构化表单。
- 解析动作不保存需求，不生成推荐。
- 用户必须确认或修改表单后再生成推荐。

## 推荐结果页

页面必须回答：

```text
推荐了什么？
为什么推荐？
哪里不足？
是否完全匹配？
如果不是完全匹配，系统如何补充推荐？
```

信息结构：

```text
用户画像摘要
-> 推荐结果列表
-> 维度解释和权重说明
-> 重新填写需求 / 反馈 / 对比入口
```

推荐分组：

- `完全匹配车型`：`matchLevel = STRICT`。
- `推荐`：非 `STRICT` 推荐项。

排序规则：

- 每组内部必须按后端 `rankNo` 升序展示。
- 不按 `totalScore`、`reputationScore`、`popularityScore` 或其他字段二次排序。
- `rankNo` 是展示排序的唯一权威。

推荐卡片必须展示：

- 排名。
- 车型图片。
- 品牌和车型名称。
- 指导价。
- 综合推荐分 `totalScore`。
- 推荐标签 `tags`。
- 推荐理由 `reasonText`。
- 不足提醒 `weaknessText`。
- 维度评分。
- 查看详情按钮。
- 加入对比。
- 收藏。

匹配状态与推荐标签必须视觉分离：

- 用户端卡片不展示 `RELAX_*` 或 `SIMILAR_RECOMMEND` 作为主要标签。
- `tags` 只展示车型优势，例如“空间优秀”“安全配置高”“价格匹配度高”。
- 管理端和历史详情可展示 `matchLevel`、`recommendStatus`、`fallbackMessage`。

加入对比交互：

- 点击“加入对比”只更新当前对比列表和按钮状态。
- 用户主动点击“查看对比（N/3）”后进入 `/compare`。
- 从对比页返回时应回到原推荐记录，并尽量恢复原位置。

反馈交互：

- 推荐结果页底部展示反馈卡片。
- 反馈提交到 `recommend_feedback`。
- 提交成功或失败在反馈卡片内展示。
- 反馈不改变推荐排序。

## 推荐生成状态

生成中状态不应只是普通 loading。建议展示：

```text
正在解析购车需求
正在计算车型匹配度
正在生成推荐理由
```

错误状态应说明问题和下一步操作，例如：

```text
推荐生成失败，请检查需求信息后重试。
```

空状态应说明原因和下一步：

```text
暂无推荐记录，您可以先填写购车需求生成推荐。
```

## 车型详情页

页面目标：展示车型完整信息，并解释该车型在推荐系统中的评分来源。

必须展示：

- 品牌。
- 车系。
- 车型名称。
- 指导价。
- 车型类型。
- 动力类型。
- 座位数。
- 上市年份。
- 车身尺寸。
- 轴距。
- 油耗或续航。
- 安全配置。
- 智能配置。
- 多维评分。

评分展示可使用雷达图或条形图。必须说明评分来源，例如空间分由轴距、车长、座位数和车型类型计算得到。

## 推荐历史

历史推荐必须展示：

- 推荐时间。
- 用户画像。
- 推荐状态。
- 补充推荐提示追溯字段。
- 推荐标签快照。
- 查看推荐明细入口。

推荐明细展示推荐发生时保存的 `tags`、分数、理由、不足和匹配状态。不要根据当前评分规则重新生成历史标签。

## 车型对比

页面目标：帮助用户查看和横向比较 1-3 款车型。

规则：

- 数据来自 `GET /api/car/compare?carIds=1,2,3`。
- 页面只读取车型基础信息、参数和车型静态评分。
- 不调用推荐生成接口。
- 不影响 `pareto-topsis-v1` 推荐排序。
- 雷达图使用八维车型静态评分：空间、安全、能耗、智能、舒适、动力、口碑、热度。
- 价格只展示在基础信息表，不放入雷达图。
- 评分缺失时显示“暂无评分，请在管理端重算评分”。

## 收藏

收藏页展示：

- 车型图片。
- 车型名称。
- 指导价。
- 车型类型。
- 动力类型。
- 查看详情。
- 取消收藏。

规则：

- 推荐结果卡片和车型详情页提供收藏入口。
- 收藏、取消收藏和状态查询使用当前用户。
- 收藏状态加载失败时不影响推荐主流程。
- 收藏成功或取消收藏后只通过按钮文字和页面内状态体现。
- 收藏只记录用户关注车型，不参与推荐排序和权重计算。

## 用户反馈

反馈表单字段：

- 满意度评分，1-5。
- 原因标签。
- 文字反馈。
- 提交成功状态。

建议原因标签：

- 价格偏高。
- 空间太小。
- 品牌不喜欢。
- 动力类型不合适。
- 配置不够。
- 油耗或续航不满意。
- 推荐结果不够准确。
- 推荐有帮助。
- 解释清楚。

反馈进入管理端统计，但不用于在线学习，不自动更新权重、车型评分或推荐排序。

## 管理端

管理端服务于推荐数据基础、推荐追溯和统计，不做复杂运营后台。

当前页面：

```text
车型管理
推荐记录
统计仪表盘
系统健康检查
算法可视化
```

车型管理页支持：

- 新增车型。
- 编辑车型。
- 删除车型。
- 维护参数。
- 查看评分。
- 重新计算评分。

推荐记录页必须展示：

- 推荐时间。
- 用户需求。
- 用户画像。
- 权重快照。
- 推荐状态。
- 补充推荐提示追溯字段。
- 推荐明细。
- 排名、车型、总分、各维度分、标签快照、匹配状态、推荐理由和不足提醒。

统计仪表盘展示：

- 预算区间分布。
- 使用场景分布。
- 显式偏好权重分布。
- 热门推荐车型。
- 推荐状态分布。
- 车型类型偏好分布。
- 动力类型偏好分布。
- 满意度分布。
- 原因标签分布。
- 反馈总数和平均满意度。

统计图表消费 `{ name, value }` 数组。没有数据时展示空状态，不展示无意义随机数据。

系统健康检查页：

- 路由为 `/admin/health`。
- 页面名称为“系统健康检查”。
- 调用 `GET /api/health`。
- 展示后端服务状态、数据库状态和检查时间。
- 提供“重新检查”按钮。
- 原始返回信息通过折叠区域展示。

## 算法可视化页面

`/algorithm-demo` 是管理端导航中的独立只读页面，用于说明推荐算法过程，不进入普通推荐主流程，不影响推荐结果生成。

页面只调用：

```text
GET /api/recommend/history
GET /api/recommend/{recordId}/algorithm-visualization
```

页面不得调用 `POST /api/recommend/generate`，不得在前端重新计算推荐排序，也不得覆盖后端 `rankNo`。

页面至少展示：

- 推荐记录选择区。
- 算法流程总览。
- 用户需求与约束。
- 车型特征评分说明。
- 主观权重、客观权重、组合权重和 `alpha`。
- 候选层级统计。
- 九维评分矩阵。
- Pareto-TOPSIS 排序信息。
- 推荐解释。
- 快照追溯说明。

该页面可以展示 TOPSIS、Pareto、熵权等术语。普通用户推荐结果页不展示这些复杂术语。

## 响应式规则

需要保证以下宽度可用：

- 1440px 桌面屏。
- 1366px 笔记本屏。
- 768px 平板宽度。

移动端做基础适配即可。文本、按钮、评分条和卡片内容不能重叠。
首页在移动端需要保证顶部导航可用、轮播内容不溢出、入口卡片单列展示。

## 验收清单

- 用户能从首页进入购车需求页。
- 用户填写需求后能看到推荐结果。
- 推荐结果页展示 `tags`、`reasonText`、`weaknessText`、维度分数和分组语义。
- 推荐结果页按 `rankNo` 展示，不二次排序。
- 用户能进入车型详情页查看参数和评分来源。
- 历史页展示推荐发生时的快照信息。
- 管理端推荐记录页能复现历史推荐依据。
- `/algorithm-demo` 只读展示权重、候选、九维矩阵、Pareto、TOPSIS、解释和快照边界。
- 普通操作反馈使用页面内状态。
- 推荐算法不写在前端。
