# 实施任务清单

本文档只描述实施阶段、任务拆分、验收标准和里程碑。项目规格见 `PROJECT_SPEC.md`，推荐闭环概要见 `RECOMMENDATION_DESIGN.md`，当前主算法细节见 `RECOMMENDATION_ALGORITHM_UPGRADE.md`，升级前算法基线和特征评分规则见 `RECOMMENDATION_ALGORITHM.md`，数据库设计见 `DATABASE_DESIGN.md`，接口设计见 `API_DESIGN.md`，前端展示和样式规则见 `FRONTEND_DESIGN.md`。

当前阶段只做规划；进入实现阶段后，应按本文档顺序推进。

## 1. 实施原则

1. 推荐闭环优先，页面和后台只服务于推荐主链路。
2. 每个阶段必须达到最低完成标准后再进入下一阶段。
3. 增强功能只在第一档功能稳定后实现。
4. 不在核心闭环完成前投入以图搜车、Redis、复杂权限或深度学习模型。
5. 推荐结果必须来自真实评分和权重计算，不允许长期依赖 mock 数据。
6. 若缺少完整真实车型数据，允许编写合理测试数据进行开发和测试，但必须保证字段取值符合常识，且推荐分仍由算法计算。
7. 每完成一个阶段或里程碑后，必须输出阶段工作汇总，说明实现内容、测试结果、遗留问题和下一步计划。

推荐闭环定义：

```text
车型参数 -> 特征评分 -> 用户画像 -> 多维匹配 -> 推荐解释 -> 降级推荐 -> 推荐记录追溯 -> 前端展示
```

### 2.1 需求模型重构说明

在继续后续功能前，需要完成一次需求模型重构，影响阶段 4、5、6、8、10 和统计展示：

- 用户需求字段从单选 `bodyType`、`energyType`、`scene` 调整为多选 `bodyTypes`、`energyTypes`、`scenes`。
- 旧 `focusFactors` 多选标签调整为 `factorWeights` 0-10 滑块，维度固定为 `price / space / safety / energy / intelligence / comfort / power / reputation / popularity`。
- 用户端需求页删除“推荐数量”输入，不让用户填写 `topK`。
- 阶段 9.5 后废弃固定 TopK、`min(5, topK)` 和默认 Top 10 截断规则，推荐生成返回全部符合分组规则的候选。
- 用户需求座位字段统一为 `minSeats` / `min_seats`，不再保留 `seats` 作为用户需求字段。
- 排除品牌和排除车型从手动输入改为基于数据库已有品牌、车型的搜索选择。
- 已确认采用重建本地库方案，旧字段 `body_type`、`energy_type`、`scene`、`focus_factors` 删除，不做长期兼容。
- 后续所有实现以 `bodyTypes`、`energyTypes`、`scenes`、`factorWeights` 为准，不实现新旧字段双写、双读或自动兼容。
- 具体执行重建本地数据库、清空表或删除联调数据前，仍必须再次说明影响并获得操作确认，不能擅自删除历史推荐记录或真实联调数据。

### 2.2 推荐算法升级说明

阶段 9.6 后当前主算法为“基于主客观组合权重与 Pareto-TOPSIS 的可解释汽车推荐算法”，算法版本为 `pareto-topsis-v1`。

- `subjectiveWeight` 来自用户显式 `factorWeights` 或 `scenes` 场景模板。
- `objectiveWeight` 来自候选集九维评分矩阵的熵权法计算。
- `finalWeight` 由 `alpha` 组合主观权重和客观权重，并保存到 `recommend_record.weight_snapshot`。
- `totalScore` 当前表示 TOPSIS 推荐分 / 综合推荐分；加权求和只作为历史算法基线、TOPSIS 边界兜底 `fallbackScore` 和升级前后对比说明。
- 推荐排序由后端写入 `rankNo`：`STRICT` 组在前，推荐组在后，每组内部先按 TOPSIS 推荐分，再按 Pareto 非支配标记、口碑分、热度分做辅助排序。
- 前端推荐结果页只按 `rankNo` 展示，不再按 `totalScore`、口碑分或热度分二次排序。

### 2.3 阶段 9.8 算法可视化说明

阶段 9.8 在不改变推荐主链路的前提下新增答辩展示能力：

- 新增只读接口 `GET /api/recommend/{recordId}/algorithm-visualization`。
- 新增独立页面 `/algorithm-demo`，首页提供低优先级入口。
- 接口只读取已有推荐记录、推荐明细、用户需求、车型参数和车型评分，不新增表、不改表结构。
- 接口不调用推荐生成流程，不写入 `recommend_record`、`recommend_item` 或 `user_demand`。
- 页面展示车型特征评分来源、硬性约束、STRICT/降级候选阶段、动态 `priceScore`、九维评分矩阵、主客观组合权重、Pareto 标记、TOPSIS 中间值、推荐解释和快照追溯。
- 普通用户推荐结果页保持简洁，仍不展示 TOPSIS、Pareto、熵权等复杂术语。

## 3. 阶段完成汇总要求

每个阶段达到最低完成标准后，进入下一阶段前必须给出工作汇总。该汇总用于确认实现边界、测试结果和后续风险，避免阶段之间遗漏关键工作。

阶段汇总模板：

```text
阶段：阶段 X - 阶段名称

完成内容：
- 实现了哪些功能
- 涉及哪些接口、表、页面或服务

主要变更：
- 主要文件或模块
- 关键设计决策

测试与验证：
- 执行的命令或手工验证步骤
- 测试结果
- 是否达到最低完成标准

遗留问题：
- 未完成事项
- 已知风险
- 需要用户确认的问题

下一步：
- 建议进入的下一阶段
- 下一阶段优先任务
```

规则：

- 不能只写“已完成”，必须说明实际完成范围。
- 测试未执行时，必须说明未执行原因和后续验证方式。
- 如果最低完成标准未完全满足，不应默认进入下一阶段，除非用户明确同意。
- 阶段汇总不替代提交记录或测试报告，但必须能让用户判断当前阶段是否可以验收。

## 9. 阶段 5：真实推荐算法

### 任务

- 根据用户需求执行严格过滤。
- 动态计算价格匹配分。
- 计算多维加权综合分。
- 生成推荐标签。
- 返回全部符合当前推荐分组规则的候选，不按固定 TopK 截断。
- 保存推荐记录和推荐明细。
- 验证 `budgetMax` 是严格阶段预算硬约束。
- 验证 `budgetMin` 是软偏好，只参与价格分计算，不过滤候选。
- 验证 `bodyTypes` 多选时匹配任一车型类型。
- 验证 `energyTypes` 多选时匹配任一动力类型。
- 验证 `energyTypes` 包含 `新能源` 时能展开匹配纯电、插混和增程。
- 验证 `tags` 持久化到推荐明细。
- 阶段 5 只实现 `STRICT` 推荐，不实现降级推荐。

### 最低完成标准

- 推荐结果来自真实评分和用户权重，不使用 mock 数据。
- 不同需求能得到不同排序。
- 结果包含总分、价格分和各维度分。

### 增强完成标准

- 支持综合分、口碑分、热度分多级排序。
- 推荐历史可复现当时分数。

### 风险点

- 推荐算法不能退化成 SQL 条件筛选。

## 10. 阶段 6：推荐解释与降级

### 任务

- 根据高权重维度和车型高分维度生成推荐理由。
- 根据高权重维度和车型低分维度生成不足提醒。
- 严格结果不足时依次执行预算、车型类型、动力类型和相似推荐降级。
- 车型类型降级基于 `bodyTypes` 的映射并集补充候选。
- 动力类型降级基于 `energyTypes` 的映射并集补充候选。
- 生成 `recommendStatus`：`SUCCESS`、`FALLBACK`、`EMPTY`。
- 按最终推荐结果中的 `recommendStatus` 和 `strictCount` 生成 `fallbackMessage` 追溯字段。
- 验证降级候选按车型去重，不覆盖严格匹配候选。
- 验证不再使用 `topK` 和 `min(5, topK)` 截断推荐结果。
- 前端按“完全匹配车型”和“推荐”分组展示。

### 最低完成标准

- 每条推荐都有推荐理由和不足提醒。
- 极端条件不返回空白页。
- 推荐结果包含匹配状态。
- 推荐记录包含正确的 `recommendStatus`。

### 增强完成标准

- 用户端弱化降级技术提示，不展示 fallbackMessage 顶部强提示。
- 推荐记录保存降级提示追溯字段。

### 风险点

- 不允许偷偷放宽用户条件。

### 风险点

- 推荐结果页不能只展示车型卡片，必须展示解释信息。

## 13. 阶段 9：管理端核心页面

### 任务

- 车型管理页：基础信息、参数维护、评分查看、评分重算。
- 推荐记录页：需求画像、推荐明细、分数、理由和匹配状态。
- 统计仪表盘页：提供需求、推荐、反馈统计入口。
- 管理端页面遵守 `FRONTEND_DESIGN.md`，保持工具型，不做复杂运营后台。

### 最低完成标准

- 车型管理页可用。
- 推荐记录页能查看推荐依据。
- 至少有基础统计入口。
- 推荐历史/推荐记录能展示历史标签、理由和匹配状态。

### 增强完成标准

- 统计图表完整。
- 推荐记录支持分页和详情查看。

### 风险点

- 管理端页面过多会拖慢核心开发。

## 14. 阶段 10：自然语言解析

### 任务

- 支持预算、多个车型类型、多个动力类型、多个场景和偏好词解析。
- 偏好词解析为 `factorWeights` 初始值，用户确认后再提交标准需求结构。
- 解析结果回填 `/recommend` 现有结构化表单，由用户确认或修改。
- 用户确认后进入标准推荐流程。
- 返回 `unsupportedTerms`、`ambiguousTerms`、`confidenceScore`，但不保存解析记录。
- 新增只读辅助接口 `POST /api/user/demand/parse-text`。

### 最低完成标准

- 能解析常见预算、多个 SUV/轿车/MPV、多个燃油/纯电/插混/增程/新能源、多个家用/通勤/长途/新手/商务场景，以及省油/空间大/安全/智能/舒适/动力强/口碑/热门/性价比等偏好词。
- 解析结果可确认修改。
- 解析接口不写入 `user_demand`、`recommend_record` 或 `recommend_item`，不直接调用推荐生成。

### 增强完成标准

- 返回 `unsupportedTerms`、`ambiguousTerms`、`confidenceScore`。
- 后续如需保存解析记录，必须先确认数据库结构变更；阶段 10 不新增表或字段。

### 风险点

- 不要追求复杂语义理解，解析错误必须允许用户修改。

## 15. 阶段 11：对比、收藏、反馈

### 任务

- 车型对比：最多 3 款车型，参数表和评分雷达图。
- 收藏：收藏、取消收藏、收藏列表。
- 反馈：满意度、不满意原因、文字反馈。
- 管理端统计：反馈数量、平均满意度、满意度分布和原因标签分布。
- 阶段 11 不修改 `pareto-topsis-v1`、TOPSIS、Pareto、熵权法、权重计算或推荐排序规则。

### 最低完成标准

- 车型对比、收藏、反馈至少一个增强功能可用，并且不影响推荐主链路。

### 增强完成标准

- 完成对比雷达图、收藏和反馈。
- 反馈进入统计页面。
- 对比页不调用推荐生成。
- 收藏不参与推荐排序。
- 反馈不用于在线学习或自动更新权重。

### 风险点

- 增强功能不能抢占推荐算法开发优先级。
- 不能把反馈包装成“算法自动学习”能力。

## 16. 阶段 12：统计与答辩打磨

### 任务

- 完成预算分布、场景分布、显式偏好权重分布、热门推荐车型、满意度、不满意原因统计。
- 统计接口响应统一使用 `{ name, value }` 数组结构。
- 准备家庭出行、城市通勤、极端降级、自然语言解析案例。
- 准备论文截图和答辩演示脚本。

### 最低完成标准

- 至少完成预算分布、场景分布、热门推荐车型 3 类统计。
- 已完成统计接口响应结构验收，前端可直接用于图表展示。
- 有完整演示流程。

### 增强完成标准

- 全部统计图表完成。
- 形成论文截图清单和答辩演示脚本。

### 风险点

- 图表数据应来自系统数据，不要完全静态造图。

## 17. 关键里程碑

### 里程碑 A：推荐数据基础完成

验收问题：系统是否已经能把车型参数转成多维评分？

包含：

- 核心表设计完成。
- 车型基础信息和参数可维护。
- 车型评分可生成。

### 里程碑 B：推荐算法闭环完成

验收问题：系统是否能根据用户需求返回真实推荐结果？

包含：

- 用户需求可提交。
- 用户画像和权重可生成。
- 推荐算法可计算排序。
- 推荐记录可保存。

### 里程碑 C：推荐可解释与可降级完成

验收问题：系统是否能说明为什么推荐，以及无匹配时如何处理？

包含：

- 推荐理由。
- 不足提醒。
- 匹配状态。
- 降级推荐。

### 里程碑 D：答辩演示闭环完成

验收问题：系统是否能完整演示从车型数据到推荐结果再到统计分析的闭环？

包含：

- 推荐结果页。
- 车型详情页。
- 管理端车型管理。
- 推荐记录追溯。
- 可选自然语言解析、对比和统计图表。

## 18. 最低交付标准

最低交付必须具备：

- 车型基础数据管理。
- 车型参数管理。
- 车型评分规则引擎。
- 结构化购车需求。
- 用户画像与权重生成。
- 真实推荐算法。
- 推荐理由与不足提醒。
- 无匹配降级策略。
- 推荐记录和推荐明细保存。
- 推荐结果页面。
- 车型详情页面。
- 管理端车型管理页面。

最低交付判断标准：

```text
推荐结果必须来自真实评分和权重计算。
推荐结果必须可解释。
无匹配时必须可降级。
推荐过程必须可追溯。
```
