# 实施任务清单

本文档只描述实施阶段、任务拆分、验收标准和里程碑。项目规格见 `PROJECT_SPEC.md`，推荐算法见 `RECOMMENDATION_DESIGN.md`，数据库设计见 `DATABASE_DESIGN.md`，接口设计见 `API_DESIGN.md`，前端展示和样式规则见 `FRONTEND_DESIGN.md`。

当前阶段只做规划；进入实现阶段后，应按本文档顺序推进。

## 1. 实施原则

1. 推荐闭环优先，页面和后台只服务于推荐主链路。
2. 每个阶段必须达到最低完成标准后再进入下一阶段。
3. 增强功能只在第一档功能稳定后实现。
4. 不在核心闭环完成前投入以图搜车、Redis、复杂权限或深度学习模型。
5. 推荐结果必须来自真实评分和权重计算，不允许长期依赖 mock 数据。
6. 若缺少完整真实车型数据，允许编写合理测试数据进行开发和测试，但必须保证字段取值符合常识，且推荐分仍由算法计算。
7. 每完成一个阶段或里程碑后，必须输出阶段工作汇总，说明实现内容、测试结果、遗留问题和下一步计划。

推荐闭环定义：

```text
车型参数 -> 特征评分 -> 用户画像 -> 多维匹配 -> 推荐解释 -> 降级推荐 -> 推荐记录追溯 -> 前端展示
```

## 3. 阶段完成汇总要求

每个阶段达到最低完成标准后，进入下一阶段前必须给出工作汇总。该汇总用于确认实现边界、测试结果和后续风险，避免阶段之间遗漏关键工作。

阶段汇总模板：

```text
阶段：阶段 X - 阶段名称

完成内容：
- 实现了哪些功能
- 涉及哪些接口、表、页面或服务

主要变更：
- 主要文件或模块
- 关键设计决策

测试与验证：
- 执行的命令或手工验证步骤
- 测试结果
- 是否达到最低完成标准

遗留问题：
- 未完成事项
- 已知风险
- 需要用户确认的问题

下一步：
- 建议进入的下一阶段
- 下一阶段优先任务
```

规则：

- 不能只写“已完成”，必须说明实际完成范围。
- 测试未执行时，必须说明未执行原因和后续验证方式。
- 如果最低完成标准未完全满足，不应默认进入下一阶段，除非用户明确同意。
- 阶段汇总不替代提交记录或测试报告，但必须能让用户判断当前阶段是否可以验收。

## 4. 阶段 0：工程骨架与约定

### 任务

- 建立 `backend`、`frontend`、`docs` 基础目录。
- 后端准备统一响应、全局异常、跨域配置、分页模型。
- 前端准备基础布局、路由、请求封装。
- 规划本地敏感配置管理：
  - `.gitignore` 忽略本地真实配置。
  - 提供 `application-local.example.yml` 示例配置。
  - 真实数据库密码只写入本地 `application-local.yml` 或环境变量。
- 固定匹配状态枚举：`STRICT`、`RELAX_BUDGET`、`RELAX_BODY_TYPE`、`RELAX_ENERGY_TYPE`、`SIMILAR_RECOMMEND`。
- 明确第一档、第二档、第三档功能边界。

### 最低完成标准

- 前后端工程可以启动。
- `GET /api/health` 可访问。
- 通用响应结构确定。
- 推荐相关服务接口结构确定。

### 增强完成标准

- README 补充启动说明。
- 前端首页显示后端连接状态。

### 风险点

- 过早引入复杂工程依赖会拖慢推荐主链路。

## 5. 阶段 1：数据库与种子数据

### 任务

- 按 `DATABASE_DESIGN.md` 建立核心表。
- 明确价格、尺寸、续航、油耗等字段单位。
- 准备最小演示数据和答辩数据扩展方案。
- 若缺少真实数据，编写合理测试数据用于开发、联调和演示。
- 固定普通用户表名为 `app_user`，外键字段仍使用 `user_id`。
- 准备默认演示用户 `app_user.id = 1`、`username = demo_user`。
- 准备默认演示管理员 `admin.id = 1`、`username = demo_admin`。
- 确保推荐记录和推荐明细能保存推荐依据。

### 最低完成标准

- 必须表结构设计完成。
- 至少规划 20 条最小演示车型数据。
- 缺少真实数据时，有明确的测试数据编写规则。
- 推荐追溯字段完整。
- 字段一致性覆盖 `user_demand.excluded_car_ids` 和 `recommend_item.tags`。
- 默认演示用户和默认演示管理员种子数据要求明确。

### 增强完成标准

- 准备 50-80 条车型种子数据。
- 覆盖 SUV、轿车、MPV、燃油、纯电、插混、增程。

### 风险点

- 车型参数缺失会导致评分引擎无法落地。
- 推荐明细字段不足会导致推荐无法追溯。

## 6. 阶段 2：车型管理与参数维护

### 任务

- 实现车型基础信息增删改查。
- 实现车型参数保存和查询。
- 管理端车型管理页合并基础信息、参数和评分入口。
- 车型参数保存后可触发评分重算。

### 最低完成标准

- 能维护车型基础信息。
- 能维护单个车型参数。
- 车型参数可被评分服务读取。

### 增强完成标准

- 车型列表支持分页和条件筛选。
- 页面提示参数完整度。

### 风险点

- 不要把车型管理扩展成复杂后台，重点是为推荐提供数据。

## 7. 阶段 3：特征评分规则引擎

### 任务

- 按 `RECOMMENDATION_DESIGN.md` 实现空间、安全、能耗、智能、舒适、动力、口碑、热度评分。
- 支持单车评分重算。
- 支持全部车型评分重算。
- 保存评分版本和计算时间。

### 最低完成标准

- 录入参数后能生成 0-100 的多维评分。
- 推荐算法可以读取评分结果。
- 单车评分可以重算。

### 增强完成标准

- 全部车型可批量重算。
- 管理端可查看评分结果。
- 缺失参数有默认分和说明。

### 风险点

- 评分规则不要过度复杂，必须能在论文和答辩中解释清楚。

## 8. 阶段 4：用户需求与画像

### 任务

- 实现结构化购车需求保存。
- 根据场景生成初始权重。
- 根据关注因素调整权重并归一化。
- 生成画像文本。
- 保存画像文本和权重快照。

### 最低完成标准

- 用户能提交结构化需求。
- 系统能生成权重向量和画像文本。
- 权重能被推荐算法使用。

### 增强完成标准

- 前端展示权重分布。
- 可快速选择典型场景模板。

### 风险点

- 关注因素主要影响排序，不应全部变成硬过滤条件。

## 9. 阶段 5：真实推荐算法

### 任务

- 根据用户需求执行严格过滤。
- 动态计算价格匹配分。
- 计算多维加权综合分。
- 生成推荐标签。
- 返回 Top 10 推荐结果。
- 保存推荐记录和推荐明细。
- 验证 `budgetMax` 是严格阶段预算硬约束。
- 验证 `budgetMin` 是软偏好，只参与价格分计算，不过滤候选。
- 验证 `新能源` 宽泛偏好能匹配纯电、插混和增程。
- 验证 `tags` 持久化到推荐明细。
- 阶段 5 只实现 `STRICT` 推荐，不实现降级推荐。

### 最低完成标准

- 推荐结果来自真实评分和用户权重，不使用 mock 数据。
- 不同需求能得到不同排序。
- 结果包含总分、价格分和各维度分。

### 增强完成标准

- 支持综合分、口碑分、热度分多级排序。
- 推荐历史可复现当时分数。

### 风险点

- 推荐算法不能退化成 SQL 条件筛选。

## 10. 阶段 6：推荐解释与降级

### 任务

- 根据高权重维度和车型高分维度生成推荐理由。
- 根据高权重维度和车型低分维度生成不足提醒。
- 严格结果不足时依次执行预算、车型类型、动力类型和相似推荐降级。
- 生成 `recommendStatus`：`SUCCESS`、`FALLBACK`、`EMPTY`。
- 按最终推荐结果生成 `fallbackMessage`。
- 验证降级候选按车型去重，不覆盖严格匹配候选。
- 验证 `topK < 5` 时使用 `min(5, topK)` 判断降级阈值。
- 前端展示匹配状态和降级提示。

### 最低完成标准

- 每条推荐都有推荐理由和不足提醒。
- 极端条件不返回空白页。
- 推荐结果包含匹配状态。
- 推荐记录包含正确的 `recommendStatus`。

### 增强完成标准

- 页面有明显降级提示横幅。
- 推荐记录保存降级提示。

### 风险点

- 不允许偷偷放宽用户条件。

## 11. 阶段 7：推荐记录追溯

### 任务

- 保存推荐记录总体信息。
- 保存推荐明细分数和解释文本。
- 实现 `GET /api/recommend/history` 轻量历史列表。
- 实现 `GET /api/recommend/{recordId}` 完整历史详情。
- 用户端可查看历史推荐。
- 管理端可查看推荐记录详情。

### 最低完成标准

- 任意一次推荐都能回查需求、权重、分数、理由和匹配状态。
- 历史记录不是只显示车型列表。
- 历史详情返回标签、理由、不足、分数和匹配状态快照，不重新计算。

### 增强完成标准

- 支持分页查看历史记录。
- 可从历史记录跳转车型详情。

### 风险点

- 不保存权重和维度分快照会导致无法复现推荐依据。

## 12. 阶段 8：用户端核心页面

### 任务

- 购车需求页：结构化表单、场景选择、关注因素多选。
- 推荐结果页：车型卡片、匹配度、标签、匹配状态、理由、不足、维度评分。
- 车型详情页：基础信息、参数、特征评分。
- 简洁首页入口：跳转购车推荐、推荐历史和管理端。
- 完整落地页作为增强任务：价值主张、推荐流程预览、算法特色说明和推荐入口。
- 页面展示和样式遵守 `FRONTEND_DESIGN.md`。

### 最低完成标准

- 用户能提交需求并查看推荐结果。
- 用户能进入车型详情。
- 页面能清楚展示推荐依据。
- 推荐结果页能展示推荐标签快照。

### 增强完成标准

- 完整落地页能在 5 秒内让用户理解系统是可解释汽车推荐系统。
- 推荐结果页展示维度条形图。
- 详情页展示雷达图。
- 完成推荐结果页、降级推荐页、评分详情页和统计页的答辩截图准备。

### 风险点

- 推荐结果页不能只展示车型卡片，必须展示解释信息。

## 13. 阶段 9：管理端核心页面

### 任务

- 车型管理页：基础信息、参数维护、评分查看、评分重算。
- 推荐记录页：需求画像、推荐明细、分数、理由和匹配状态。
- 统计仪表盘页：提供需求、推荐、反馈统计入口。
- 管理端页面遵守 `FRONTEND_DESIGN.md`，保持工具型，不做复杂运营后台。

### 最低完成标准

- 车型管理页可用。
- 推荐记录页能查看推荐依据。
- 至少有基础统计入口。
- 推荐历史/推荐记录能展示历史标签、理由和匹配状态。

### 增强完成标准

- 统计图表完整。
- 推荐记录支持分页和详情查看。

### 风险点

- 管理端页面过多会拖慢核心开发。

## 14. 阶段 10：自然语言解析

### 任务

- 支持预算、车型、动力、场景、关注因素解析。
- 解析结果进入确认修改页面。
- 用户确认后进入标准推荐流程。
- 增强项保存解析记录和置信度。

### 最低完成标准

- 能解析常见预算、SUV/轿车/MPV、燃油/纯电/插混/增程/新能源、家用/通勤/长途/新手、省油/空间大/安全/智能/舒适/动力强。
- 解析结果可确认修改。

### 增强完成标准

- 返回 `unsupportedTerms`、`ambiguousTerms`、`confidenceScore`。
- 保存解析记录。

### 风险点

- 不要追求复杂语义理解，解析错误必须允许用户修改。

## 15. 阶段 11：对比、收藏、反馈

### 任务

- 车型对比：最多 3 款车型，参数表和评分雷达图。
- 收藏：收藏、取消收藏、收藏列表。
- 历史：推荐历史和明细查看。
- 反馈：满意度、不满意原因、文字反馈。

### 最低完成标准

- 至少完成车型对比或历史记录一个增强功能。

### 增强完成标准

- 完成对比雷达图、收藏和反馈。
- 反馈进入统计页面。

### 风险点

- 增强功能不能抢占推荐算法开发优先级。

## 16. 阶段 12：统计与答辩打磨

### 任务

- 完成预算分布、场景分布、关注因素分布、热门推荐车型、满意度、不满意原因统计。
- 统计接口响应统一使用 `{ name, value }` 数组结构。
- 准备家庭出行、城市通勤、极端降级、自然语言解析案例。
- 准备论文截图和答辩演示脚本。

### 最低完成标准

- 至少完成预算分布、场景分布、热门推荐车型 3 类统计。
- 已完成统计接口响应结构验收，前端可直接用于图表展示。
- 有完整演示流程。

### 增强完成标准

- 全部统计图表完成。
- 形成论文截图清单和答辩演示脚本。

### 风险点

- 图表数据应来自系统数据，不要完全静态造图。

## 17. 关键里程碑

### 里程碑 A：推荐数据基础完成

验收问题：系统是否已经能把车型参数转成多维评分？

包含：

- 核心表设计完成。
- 车型基础信息和参数可维护。
- 车型评分可生成。

### 里程碑 B：推荐算法闭环完成

验收问题：系统是否能根据用户需求返回真实推荐结果？

包含：

- 用户需求可提交。
- 用户画像和权重可生成。
- 推荐算法可计算排序。
- 推荐记录可保存。

### 里程碑 C：推荐可解释与可降级完成

验收问题：系统是否能说明为什么推荐，以及无匹配时如何处理？

包含：

- 推荐理由。
- 不足提醒。
- 匹配状态。
- 降级推荐。

### 里程碑 D：答辩演示闭环完成

验收问题：系统是否能完整演示从车型数据到推荐结果再到统计分析的闭环？

包含：

- 推荐结果页。
- 车型详情页。
- 管理端车型管理。
- 推荐记录追溯。
- 可选自然语言解析、对比和统计图表。

## 18. 最低交付标准

最低交付必须具备：

- 车型基础数据管理。
- 车型参数管理。
- 车型评分规则引擎。
- 结构化购车需求。
- 用户画像与权重生成。
- 真实推荐算法。
- 推荐理由与不足提醒。
- 无匹配降级策略。
- 推荐记录和推荐明细保存。
- 推荐结果页面。
- 车型详情页面。
- 管理端车型管理页面。

最低交付判断标准：

```text
推荐结果必须来自真实评分和权重计算。
推荐结果必须可解释。
无匹配时必须可降级。
推荐过程必须可追溯。
```

## 19. 增强交付标准

增强交付包括：

- 自然语言需求解析。
