# 项目规格说明

## 1. 项目定位

项目名称建议为：

> 基于主客观组合权重与 Pareto-TOPSIS 的可解释汽车购买推荐系统

系统面向普通购车用户，定位为汽车购买决策辅助平台。系统通过采集用户预算、可接受车型类型集合、可接受动力类型集合、最低座位数、使用场景集合和九维显式偏好权重，生成用户购车画像；再结合车型参数和车型多维特征评分，计算车型与用户需求之间的匹配度，并输出推荐理由、不足提醒和匹配状态。

系统不是汽车商城、4S 店管理系统或真实交易平台，不涉及下单、支付、贷款、保险、经销商结算、复杂营销活动或真实成交价预测。

当前项目已进入交接维护阶段。后续开发者应先阅读 `DEVELOPMENT_GUIDE.md`、`SYSTEM_CONTRACTS.md` 和 `HANDOFF.md`，再进入具体专项文档。本文档继续维护项目定位、范围边界和功能优先级，不重复维护接口字段、数据库字段或完整算法公式。

## 2. 最高优先级

项目最高优先级是推荐算法及其工程化实现。所有功能都必须服务于推荐主链路：

```text
车型参数 -> 特征评分 -> 用户画像 -> 多维匹配 -> 推荐解释 -> 降级推荐 -> 推荐记录追溯
```

判断系统是否成立的标准不是页面数量，而是：

- 推荐结果是否来自真实车型评分和用户权重计算。
- 推荐结果是否说明为什么推荐、哪里不足。
- 无严格匹配结果时是否能降级推荐。
- 推荐记录是否能回查需求、权重、分数、理由和匹配状态。

当前主算法统一表述为“基于主客观组合权重与 Pareto-TOPSIS 的可解释汽车推荐算法”，算法版本为 `pareto-topsis-v1`。系统先将车型参数映射为车型特征评分向量，再将用户需求映射为 `subjectiveWeight`，同时使用熵权法根据候选集差异计算 `objectiveWeight`，通过 `alpha` 组合得到 `finalWeight`。排序阶段使用 TOPSIS 相对接近度计算 `totalScore`，并保留 Pareto 非支配标记作为同分辅助排序和算法追溯信息，同时基于贡献度和理想解差距生成推荐理由和不足提醒。该算法属于可解释的内容特征推荐和多指标决策方法，不采用协同过滤、深度学习推荐或在线学习推荐。

## 3. 功能优先级

### 3.1 第一档：必须完成

第一档功能决定项目是否成立，不能砍：

1. 车型基础数据管理
2. 车型参数管理
3. 车型特征评分规则引擎
4. 结构化购车需求表单
5. 用户画像与权重生成
6. 真实推荐算法
7. 推荐理由与不足提醒
8. 无匹配降级策略
9. 推荐记录与推荐明细保存
10. 推荐结果页面
11. 车型详情页面
12. 管理端基础车型维护页面

### 3.2 第二档：建议完成

第二档功能用于提升答辩效果：

1. 自然语言需求解析
2. 车型对比雷达图
3. 收藏与历史记录
4. 用户反馈
5. 后台统计仪表盘

自然语言解析只需支持常见购车表达，例如预算、SUV/轿车/MPV、燃油/纯电/插混/增程/新能源、家用/通勤/长途/新手、省油/空间大/安全/智能/舒适/动力强。

### 3.3 第三档：论文展望

以下功能不纳入核心实现：

- 以图搜车
- Redis 缓存
- Swagger/Knife4j 完整接口文档
- Excel 批量导入
- 复杂权限系统
- 在线学习推荐
- 深度学习推荐模型

## 4. 角色与页面范围

### 4.1 普通用户

普通用户主要完成：

- 提交购车需求
- 查看推荐结果
- 查看车型详情
- 查看历史推荐
- 对比车型
- 收藏车型
- 提交反馈

### 4.2 管理员

管理端只保留 3 个核心页面：

1. 车型管理：基础信息、参数维护、评分查看和评分重算。
2. 推荐记录：查看需求画像、推荐明细、分数、理由和匹配状态。
3. 统计仪表盘：展示需求、推荐和反馈统计。

管理端不扩展成复杂后台系统。

### 5.3 第一版认证策略

第一版采用“演示用户优先”策略，不让登录系统阻塞推荐闭环：

- 用户端接口允许传 `userId`。
- 如果 `userId` 为空，后端使用默认演示用户。
- 管理端第一版可先使用演示管理员或简化入口。
- 默认演示用户为 `app_user.id = 1`。
- 默认演示管理员为 `admin.id = 1`。
- JWT 登录认证作为后续增强项，不作为第一档功能的阻塞条件。

## 8. 最低验收标准

项目最低交付必须满足：

- 第一档功能全部完成。
- 推荐结果来自真实评分和用户权重计算。
- 推荐结果可解释。
- 无匹配时可降级。
- 推荐过程可追溯。
- 前端至少完成购车需求页、推荐结果页、车型详情页和管理端车型管理页。

完整落地页属于前端体验增强项，不阻塞第一档推荐闭环。实现顺序上，推荐结果页和购车需求页优先级高于完整落地页。

## 9. 数据不足时的处理原则

如果开发阶段缺少完整真实车型数据，可以编写合理的测试数据用于开发、调试、演示和论文流程验证。

测试数据必须遵守以下原则：

- 字段取值应符合常识，例如价格、轴距、续航、油耗、座位数不能明显失真。
- 数据应覆盖主要车型类型、动力类型、价格区间和使用场景。
- 推荐评分仍必须由参数规则计算生成，不能直接手工指定最终推荐分。
- 论文或答辩中需要说明测试数据用于系统功能验证，不代表真实市场销量、口碑或成交表现。
- 如果某些字段缺失，可以使用合理默认值，但应在文档或代码注释中说明默认值来源。

## 10. 本地敏感配置原则

真实数据库账号、密码和其他敏感信息不得写入项目文档或提交到仓库。

建议做法：

- 仓库只保留示例配置，例如 `application-local.example.yml`。
- 本地真实配置写入 `application-local.yml` 或环境变量。
- `application-local.yml`、`.env`、`.env.local` 必须加入忽略规则。
- 文档中只能使用 `your_mysql_password` 这类占位符。

## 11. 答辩演示主线

建议答辩按以下顺序演示：

1. 管理端查看车型参数和车型评分。
2. 用户提交结构化购车需求；阶段 10 完成后可补充自然语言解析确认演示。
3. 系统生成用户画像和权重。
4. 系统生成推荐结果。
5. 展示推荐理由、不足提醒和匹配状态。
6. 展示极端条件下的降级推荐。
7. 查看推荐记录追溯。
8. 可选展示车型对比、用户反馈和统计仪表盘。
